# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this module.

It is the **public** half of the project's guidance: architecture, features, build and test
mechanism — everything a contributor needs. Operational material (the live test-box inventory,
connection details, provisioning state) is deliberately not here.

## What this is

> **A note on `sql/` paths in this file.** Several passages below name DDL scripts under `sql/`
> — the fixtures behind the live-database tests. **Those are not in the published repository.**
> They carried the schema layout of third-party systems, which is not ours to hand out, so the
> whole tree stays private rather than part of it. The generator, the runtime library and the
> database-free suite are complete without them; what you lose is the ready-made fixtures for
> the *gated* tests, which skip when no database is reachable. `Scripts/check_provisioning.sh`
> will name the exact objects a given config expects, which is the place to start if you want
> to build equivalents. See `CONTRIBUTING.md`.


MCPDBWizard: a Swing desktop application and code generator that introspects Oracle PL/SQL (packages, procedures, functions, sequences, tables) and emits Java JDBC wrapper code — DAO factories, callable-statement wrappers, table managers, and optionally JSON / JSON-RPC web-service connectors. The generated code depends at runtime on the `com.mcpdbwizard.pub` support library, which is part of this same repo.

## Build & run

```bash
mvn clean package          # compiles + produces both jars
mvn compile                # compile only
```

`package` produces two artifacts:
- `target/mcpdbwizard-app.jar` — plain jar (manifest main class set, but needs ojdbc5 on the classpath)
- `target/mcpdbwizard-app-2.0.0-shaded.jar` — self-contained runnable jar with the Oracle driver bundled

Run the application (entry point `com.mcpdbwizard.app.procbuilder.gui.ProcBuilder`):

```bash
# Interactive (Swing) mode:
java -jar target/mcpdbwizard-app-2.0.0-shaded.jar <log_dir> <config>.pb2
# Batch mode:
java -jar target/...-shaded.jar <log_dir> build <config>.pb2
```

The first arg is a writable log directory (created if missing). Config files use the `.pb2` extension **or the newer `.json` format** — see "JSON config format" below; both interactive and batch mode accept either, chosen by file extension.

**There used to be a leading `<access_code>` argument, REMOVED 2026-08.** It was validated for shape (≥19 chars, not a path, not the literal `build`) and then handed to `ApplicationShell`, whose constructors ignored it — never stored, compared or read, so any conforming string worked and it authenticated nothing. The checks were an argument-order guard (`build`, a colon, a dot, a slash and an absolute path are what you get when the log directory or a filename is passed first), left over from a licensing scheme this code no longer has. It was removed rather than kept because publishing a generator whose first argument is a meaningless secret invites one question from every contributor, and because it tripped the export leak gate as a credential-shaped literal. **A command line that still passes one now reads it as the log directory** — the failure is a log directory named `P6uxbe05...`, not an error.

### User SQL statements live IN the config (`SQL_TEXT_<i>`)

A config used to store only `SQL_FILENAME_<i>` — a bare name — plus one global `SQL_FILE_DIRECTORY`,
with the statements on disk. That is why the committed propfiles still carry
`SQL_FILE_DIRECTORY=C:\DR\Work\CodeSpooks\Sqlfiles`, an absolute path on a machine that has not
existed for years, why `testrun_current.sh` and the web app each rewrite that directory before they
can generate, and why SQL files "go missing". **Since 2026-08-15 a config carries the statement
itself in `SQL_TEXT_<i>`, and all 41 committed propfiles have been migrated.**

**`SQL_FILENAME_<i>` STAYS, and keeps its `.sql` suffix — it is not redundant.** It is the
statement's identity and the source of its generated class name: `SqlStatementWrangler` derives that
name by removing a fixed **four** characters, so `update5.sql` becomes `Update5` (plus
`Update5Cursor`, `Update5CursorAttr`, and the MCP tool name) while a bare `update5` would silently
become `Upda`. Do not "tidy" the suffix away.

**Reading:** inline text wins over a file of the same name — a config carrying its statement is
self-contained, and a stale file beside it must not take precedence. A config with no `SQL_TEXT_<i>`
falls back to the directory exactly as before, so old configs are unaffected. The loader also MERGES
the two sources (`ApplicationShell.mergeInlineSqlNames`): the SQL tab has always been populated by
listing a directory, so without that a config carrying its own text would show nothing.

**Writing:** `SqlStatementWrangler.writeProperties` emits `SQL_TEXT_<i>` from
**`theOriginalStatement`** — the text exactly as read — and NOT from `getRawSqlStatement()`, which
returns the form already through `cleanUpCommand`/`sqlplusParams`. `cleanUpCommand` escapes a double
quote, so persisting the processed form would turn `\"` into `\\"` on the next save and again on
the one after: a statement that degrades slightly every time anyone presses save. `InlineSqlWriteTest`
pins this, and reverting the write to the processed form fails three of its five tests.

**Migrating a config** (customers' own included): `com.mcpdbwizard.schema.SqlInliner`, which searches
the given directories in order — first match wins, so an overlay sits in front of a shared library —
and **appends** to a `.pb2` rather than rewriting it, because these files are 2011 `store()` output in
hash order and a rewrite would bury the change in a reordering of every line. Idempotent: a statement
that already has its text is left alone. A file it cannot find is REPORTED and skipped, never fatal.

```sh
java -cp <jar> com.mcpdbwizard.schema.SqlInliner <config.pb2|.json> <sqlDir> [<sqlDir> ...]
```

**The four `queryXml.sql` references that will not migrate are correct.** They carry
`SQL_CREATE_CLASS=NO`, so the entry is a **deselection** — an unnamed `.sql` in the directory
defaults to generating, so deleting the reference would silently start generating `queryXml.sql` the
day somebody adds it. `DanglingSqlFileCensusTest` pins the count at 4.

**Verified as a MOVE, not an edit:** regenerating `generic_test1` + `generic_test5` from the migrated
configs — statements now read from the config rather than from `Sqlfiles/` — produces output
**byte-identical** to the pre-migration baseline, 2492 files including all 52 SQL-derived classes.

`SQL_FILE_DIRECTORY` is now a **fallback**, kept because customer configs written before this still
rely on it. It is still written on save for older readers.

### JSON config format (`com.mcpdbwizard.schema`)

A `.pb2` config is a flat `java.util.Properties` file (indexed keys like `PROC_NAME_<i>`, `SQL_PARAM_NAME_<i>_<m>`). The `com.mcpdbwizard.schema` package models the same request as typed, JSON-friendly Java objects so a config can also be authored/stored as JSON. `Schema` holds the ~74 high-level scalar settings as `String` fields (a `.pb2` stores everything as text, so String preserves each value exactly and round-trips) plus typed lists of `Sequence` / `Table` / `Procedure` / `SqlStatement` (with nested `SqlParam`); any unrecognised key is kept verbatim in `extraProperties` for a lossless round-trip. It offers a null ctor, full ctor, JSON ctor `Schema(String)`, PB2-file ctor `Schema(File)`, `Schema(Properties)`, `toPb2()`/`writePb2(File)`, and `toJson()`; JSON (de)serialisation goes through the small dependency-free `Json` reader/writer in the same package (no external lib). **Round-trip contract:** `new Schema(props).toPb2()` reproduces a `Properties` equal to the original (a `.pb2` is order- and comment-independent); a null scalar field means the key was absent and stays absent, an empty string means present-but-empty. The application reads either format through one funnel — `ApplicationShell.loadConfig(String)` (used by `getIniFile()`) detects `.json` via `isJsonConfig` and expands it through `Schema.toPb2()`, so every downstream code path is unchanged; the interactive `setIniFile()` save mirrors this, writing JSON when the config filename ends in `.json`. Every committed `Propfiles/*.pb2` has a generated `.pb2`-equivalent `.json` sibling. A CLI converter is provided both ways (direction chosen by extension): `java -cp <jar> com.mcpdbwizard.schema.ConfigConverter in.pb2 out.json` (or `in.json out.pb2`). Tests: `SchemaRoundTripTest` (PB2→Schema→PB2 and PB2→Schema→JSON→Schema→PB2 over all propfiles, `extraProperties` empty for every one) and `JsonConfigLoadTest` (the app's `loadConfig` yields identical properties from a `.json` and its `.pb2` sibling). **`Scripts/json-config-test/run.sh [propfile]`** is a live regression leg (default `generic_test2` against ORCL12; env `MCPDBWIZARD_TEST_HOST`/`PORT`/`SID`/`VERSION`, needs the shaded jar): it rewrites the connection, derives a `.json` via `ConfigConverter`, generates the schema off both the `.pb2` and the `.json`, and asserts the generated **code is byte-identical** (comment blocks — which hold the run-to-run timestamp and rotating "Tips" blurb — are stripped before the diff). Self-skips if the DB is unreachable.

- **Java 21** (`maven.compiler.release`). Maven itself may run on a newer JDK; that's fine.
- The Oracle JDBC driver is **`com.oracle.database.jdbc:ojdbc11:23.26.2.0.0`**, pulled from Maven Central. It supports Oracle Database 12c–23ai/26ai and provides the `oracle.jdbc.OracleType.JSON/VECTOR/BOOLEAN` and `oracle.sql.json.*` APIs that the 23ai datatypes need (see "Oracle 23ai datatype support" below). (Upgraded 2026-07-21 from 23.7.0.25.01; the 23.26 line matches the 26ai server generation and adds the sparse-VECTOR accessor 23.7 lacked — `oracle.sql.VECTOR.isSparse()`/`toSparseDoubleArray()` + `SparseFloatArray.of(...)`. Regressed green on 12c/21c/23ai. The `xdb`/`xmlparserv2` optional deps track the same 23.26.2.0.0.) The legacy `com.oracle:ojdbc5:11.2.0.4` that this project used against Oracle 11 is **retained under `repo/`** (a project-local file repository wired in via the `<repositories>` block) for reference, but is no longer on the build path — it cannot talk to a 23ai server for the new datatypes. To reinstate it locally: `mvn install:install-file -Dfile=lib/ojdbc5.jar -DgroupId=com.oracle -DartifactId=ojdbc5 -Dversion=11.2.0.4 -Dpackaging=jar -DlocalRepositoryPath=repo`.

### Oracle 23ai datatype support

`com.mcpdbwizard.pub` was written against Oracle 11; it now also recognises the post-11 column types. `SqlUtils.getUnderlyingOracleDatatype` classifies them and `ReadOnlyRowSet.unloadObject` reads them:

- **Native `BOOLEAN`** (23ai) → `SqlUtils.ORACLE_NATIVE_BOOLEAN_DATATYPE` (distinct from the PL/SQL-only `ORACLE_BOOLEAN_DATATYPE`); read via `getBooleanObj` / `getBoolean`.
- **Native `JSON`** (21c+) → `ORACLE_JSON_DATATYPE`; read via `ReadOnlyRowSet.getJSON(...)` → `oracle.sql.json.OracleJsonValue`.
- **`VECTOR`** (23ai). **Dense** `VECTOR(n, FLOAT32/FLOAT64/INT8)` and **flexible** `VECTOR(*,*)` → `ORACLE_VECTOR_DATATYPE`, read via `ReadOnlyRowSet.getVector(...)` → `double[]`. **Binary** (bit-packed) `VECTOR(n, BINARY)` → `ORACLE_VECTOR_BINARY_DATATYPE`, read via `getVectorBinary(...)` → `byte[]` (n bits = n/8 bytes; the driver rejects `double[]` with `ORA-17004`). **Sparse** `VECTOR(n, t, SPARSE)` → `ORACLE_VECTOR_SPARSE_DATATYPE`, read via `ReadOnlyRowSet.getVectorSparse(...)` → **`com.mcpdbwizard.pub.SparseVector`** (a `{length, indices[], values[]}` value class), written via `WriteableRowSet.setVectorSparse(...)` / `StatementParameters2.setVectorSparseParam(...)`. **Implemented** (2026-07-21, unblocked by the ojdbc11 23.7→23.26.2.0.0 upgrade): the driver's `oracle.sql.VECTOR.isSparse()`/`toSparseDoubleArray()` (→ `{length, indices, values}`) and `VECTOR.ofFloat64Values(VECTOR.SparseDoubleArray.of(len, idx, vals))` back the read/write. **Detection wrinkle:** a sparse column carries the SAME JDBC metadata as a dense one (`getColumnType()` = `VECTOR_FLOAT32` for both — unlike binary's distinct `VECTOR_BINARY`), so the `ORACLE_VECTOR_DATATYPE` row/OUT unload reads the value as an `oracle.sql.VECTOR` and dispatches on `isSparse()` (sparse → `SparseVector`, preserved not densified; dense → `double[]`; binary → `byte[]` on `ORA-17004`). The writer is format-agnostic — it always binds `ofFloat64Values` and lets Oracle coerce to the column/param element format (an `INT8` column rounds fractional values). Sparse generation is covered in "VECTOR sub-formats" below. **FLOAT16** is separate — server-blocked (`ORA-51802` on 26ai Free 23.26; the DB version has no FLOAT16 format), so no driver can help. At runtime `ReadOnlyRowSet` tells binary from dense via `ResultSetMetaData.getColumnType()` (`OracleTypes.VECTOR_BINARY`), since `getColumnTypeName()` is just `"VECTOR"` for every format. Full design/driver notes in `docs/oracle23ai-vector-subformats-plan.md`.
- 12c **`IDENTITY`** columns ride the existing NUMBER path; 12c **extended `VARCHAR2`/`RAW`** (32k) ride the TEXT/RAW paths but need `MAX_STRING_SIZE = EXTENDED` server-side. The standing boxes' default PDBs are all `STANDARD` (so the shared DDL caps at 4000); a dedicated **EXTENDED PDB `EXTPDB1`** exists on the FREE23 box (`.../<host>:1521/extpdb1`, <user>/<password>, created by `sql/make_extpdb1.sql` — run it on the box console as sysdba to rebuild). `Varchar32kLiveTest` covers the 4000/4001/32767 boundaries against it and **self-gates on ORA-00910**, so it skips (never fails) on STANDARD servers. The *generator* was also verified against EXTPDB1 (2026-07-15, one-time): a `VARCHAR2(32767)`/`RAW(32767)` table generates a normal `String`/`byte[]` DAO that compiles and round-trips 32767-char/-byte values through insert/select/update/delete — extended lengths need no generator changes (nothing branches on column length).

DDL for these lives in `sql/datatypes_23ai.sql` (idempotent, run as the test schema owner).

**Write-back (`com.mcpdbwizard.pub`).** Writing the new types is now implemented: `WriteableRowSet` has `setJSON`/`setVector`/`setBoolean`; `StatementParameters2` binds them in `bindParameters` (`setObject(i, v, OracleType.JSON/VECTOR/BOOLEAN)`), with new `setParam(OracleJsonValue)` / `setParam(double[])` / `setNativeBooleanParam(Boolean)` setters — the native-boolean path is **distinct** from the legacy PL/SQL `setParam(int, Boolean)` (which still passes a ±1 number); `CallableStatementParameters` registers + unloads JSON/VECTOR/BOOLEAN OUT params via the int `OracleTypes.JSON/VECTOR/BOOLEAN` codes. **Binary vectors** are written through a distinct path (a `byte[]` is ambiguous with RAW): `WriteableRowSet.setVectorBinary(byte[])` and `StatementParameters2.setVectorBinaryParam(int, byte[])` type the bind as `OracleType.VECTOR_BINARY` (a plain `byte[]` still binds RAW); `CallableStatementParameters` unloads a `VECTOR_BINARY` OUT param as `byte[]`.

**Generator support (the wizard now *emits* code for these types).** The generator was Oracle-11-only and hard-stopped on the new types; it now generates compilable read+write wrappers across table DAOs, callable statements (procedures/functions), and the SOAP web-service layer:
- `app.common.DatatypeWrangler.getOracletypeCode` maps `JSON`/`BOOLEAN`/`VECTOR` → `OracleTypes.JSON/BOOLEAN/VECTOR` (was: throw "Unknown data type").
- `app.common.JavaUtils.oracle2JavaDatatype` maps the new `SqlUtils` constants → `oracle.sql.json.OracleJsonValue` / `Boolean` / `double[]`. This alone clears the `SAAdminWrangler` table-skip (it throws on any column that resolves to `"Object"`).
- `CallableStatementParameterEngine` got JSON/VECTOR/BOOLEAN arms in its variable-type switch, the IN-bind ladder (native boolean → `setNativeBooleanParam`), and the SOAP scalar pass-through group (mirroring the `SDO_GEOMETRY` recipe).
- `SqlStatementWrangler` (table INSERT/UPDATE statements): `ASP_DATA_TYPES` gained `BOOLEAN`/`JSON`/`VECTOR` tokens and the comment-hint parser maps `oracle.sql.json.OracleJsonValue`→`JSON`, `double[]`→`VECTOR`. (The ASP token doubles as the `DATA_TYPE` fed to the engine — see `getDualQuery`.)
- `SAAdminWrangler.getVersion()` now falls back to the newest known version's data-dictionary SQL when the banner matches no known version substring (23ai/26ai banners like `23.26.0.0.0` contain none), instead of NPEing on a null version.

**VECTOR sub-formats in generated code (binary → `byte[]`).** The generator emits working DAOs for **binary** vector *table columns*, not just dense ones. The problem: `ALL/USER_TAB_COLUMNS.DATA_TYPE` is `"VECTOR"` for *every* format — the format is only in the `VECTOR_INFO` descriptor. So the table-column introspection queries (`SqlStatementDictionary.getAllTabColsQry`/`getAllTabColsCSEQry`, gated by `SAAdminWrangler.isVectorInfoAvailable()`) rewrite a binary column's `DATA_TYPE` to a **synthetic `VECTOR_BINARY` token** (a shared `vectorFormatDataType` `CASE` on `VECTOR_INFO`; sparse → `VECTOR_SPARSE`). That token then flows through every `DATA_TYPE`-keyed site: `SqlUtils.getUnderlyingOracleDatatype` → `ORACLE_VECTOR_BINARY_DATATYPE`, `JavaUtils` → `byte[]`, `DatatypeWrangler` → `OracleTypes.VECTOR_BINARY`, the engine's variable-type/SOAP/IN-bind arms (emitting `setVectorBinaryParam`). **Keystone:** the generated INSERT/UPDATE SQL *comment* seeds the ASP token and is written from the Java type — but `byte[]` is ambiguous with RAW, so `SAAdminWrangler`'s comment writer emits the `VECTOR_BINARY` token for a binary column instead of `byte[]`, making the whole ASP→bind chain resolve to `setVectorBinaryParam` rather than a RAW `setParam`. Dense/flexible `VECTOR` generation is byte-identical. **Sparse** columns are now generated too (2026-07-21): the `VECTOR_SPARSE` token threads exactly like `VECTOR_BINARY` (→ `JavaUtils` `com.mcpdbwizard.pub.SparseVector`, `DatatypeWrangler` `OracleTypes.VECTOR`, the comment-writer emits `VECTOR_SPARSE`, and INSERT/UPDATE binds via `setVectorSparseParam`), so a sparse column generates a `SparseVector` DAO field that reads through `processMany`'s generic `(SparseVector)theArray[n]` cast. The two former skip guards (the `SAAdminWrangler` table-column loop's `Table being ignored` on a sparse column, and `JavaUtils`' `"Object"` fallthrough) were removed. **Proc params are format-flexible, and the generated wrappers now expose ALL THREE forms:** PL/SQL forbids format-constrained parameters (`p IN VECTOR(16, BINARY)` is PLS-00103), so a `VECTOR` parameter has no fixed format — the format travels with the value. Every generated vector param therefore gets a dense setter (`setParamX(double[])`), a binary overload (`setParamX(byte[])`, bound via `setVectorBinaryParam`), and a sparse overload (`setParamX(com.mcpdbwizard.pub.SparseVector)`, bound via `setVectorSparseParam`) — the three clear each other so the last-set form wins; the IN-bind dispatch is sparse→binary→dense. On the OUT side an instanceof dispatch fills `getParamX()` (double[]) / `getParamXVectorBinary()` (byte[]) / `getParamXVectorSparse()` (SparseVector) — backed by `CallableStatementParameters`' VECTOR unload, which peeks the raw `oracle.sql.VECTOR` and returns a `SparseVector` when `isSparse()`, else falls from `double[]` to `byte[]` on ORA-17004. Emission gotcha: some non-scalar rows (records/collections through the ASP comment-hint path) can classify as VECTOR in `oracleUnderlyingDatatype`, so every vector arm in `CallableStatementParameterEngine` is guarded with `variableDataType[i].equals("double[]")`. `TGen23ai` round-trips a `VECTOR(16,BINARY)` column (read `byte[]`), a `VECTOR(25,FLOAT32,SPARSE)` column (read `SparseVector`), and both binary and sparse forms through `vector_echo`'s `VECTOR` params; the write binds are covered by `Datatypes23aiLiveTest`. **MCP:** a sparse *table column* crosses as a `{length, indices, values}` JSON object (via `RECORD_MAPPER`); a sparse *proc param* is NOT exposed over MCP (a VECTOR proc tool stays dense-array only — see `docs/mcp-sparse-vector-plan.md` I4). Only **FLOAT16** vectors remain unsupported (server-blocked, `ORA-51802`).

**23ai `ALL_PLSQL_TYPE_ATTRS` scalar-name normalization (residual nested-type variant, fixed 2026-07-16).** The record-field synthesis reads field types from `ALL_PLSQL_TYPE_ATTRS`, which spells some scalars in ways `ALL_ARGUMENTS` never did: `PL/SQL BINARY INTEGER` (also what `NATURAL/POSITIVE/SIGNTYPE` subtypes report as), `PL/SQL PLS INTEGER`, `PL/SQL LONG`, `PL/SQL ROWID`, `TIMESTAMP WITH TZ`, `TIMESTAMP WITH LOCAL TZ`. An unrecognised name NPEs downstream, the engine's outer catch swallows it, and the record class is **silently skipped** — surfacing as a missing `*Attrs` SOAP companion (AXISTEST's `ART` record in `generic_test8` was the reproducer: 71 files on 23ai vs 73 on 12c). `SqlStatementDictionary.plsqlAttrDataTypeDecode` maps all of these back to the `ALL_ARGUMENTS` spellings and is applied by **every** synthesis arm that selects `a.attr_type_name` as `DATA_TYPE` (the record-field arm and the record-as-collection-element arm).

**JSON-relational duality views (23ai) are now handled.** Duality views were already *discoverable* (the table-list query includes `object_type = 'VIEW'`) and even generated compilable-but-inert output (a DV presents as a view with exactly one JSON column — usually `DATA` — and **no constraints**, so none of the constraint-driven table methods emitted). `SAAdminWrangler` now feature-detects `ALL_JSON_DUALITY_VIEWS` (probe + cached flag; pre-23ai untouched) and, per table, `SqlStatementDictionary.getJsonDualityViewQry` identifies a DV plus its `JSON_COLUMN_NAME` and `ALLOW_INSERT/UPDATE/DELETE` flags. `addDualityViewDocMethods` then emits **document-level CRUD** into the ordinary manager class: `docGetAll()` / `docGetById(String)` always, and `docInsert(OracleJsonValue)` / `docUpdate(OracleJsonValue)` / `docDelete(String)` only when the view allows the operation. Documents are keyed on the server-maintained `_id` (`JSON_VALUE(<col>, '$._id' RETURNING VARCHAR2(4000))`); `docUpdate` is a full-document replace that extracts `_id` from the document client-side. The SQL statements are written as `.TSQ` files, so the ordinary `SqlStatementWrangler` pass builds the statement classes (`*DocAll/DocById/DocIns/DocUpd/DocUpdChk/DocDel`). **`docUpdate` is etag optimistic-locked** (added after v1): when the document carries `_metadata.etag` — as every document read through the view does — the update runs through `*DocUpdChk`, whose WHERE clause also matches `JSON_VALUE(<col>, '$._metadata.etag')`; zero rows updated means the stored document changed (or vanished) since it was read, and the manager throws the new `com.mcpdbwizard.pub.CSDocumentChangedException` (recover by re-reading and reapplying). A document **without** `_metadata` replaces unconditionally (last-writer-wins) — stripping `_metadata` is the forced-overwrite escape hatch. Row-count detection rides a uniform generated-`AbstractSqlStatement` template addition: `issueCall` stores `executeUpdate()`'s return and `getRowsAffectedCount()` exposes it (every generated package gains it, like the generated-key hook). Note the server would also reject a stale *embedded* etag itself (ORA-42699, verified live), but the generated code doesn't rely on that — the WHERE predicate keeps failure detection deterministic and error-parse-free. **Composite `_id` documents are also handled** (multi-column root-table PK → `_id` is a JSON *object* with one field per PK column, which `JSON_VALUE` can't match — the pre-fix behavior was a silent zero-row miss on every keyed doc method): the DV query now also returns `ROOT_TABLE_OWNER/NAME` and `SqlStatementDictionary.getPkColCountQry` counts the root PK's columns (a two-view `ALL_CONSTRAINTS`+`ALL_CONS_COLUMNS` join — safe because it only runs behind the 23ai duality-view gate, never on 19c); PK count > 1 flips the emission to `WHERE JSON_EQUAL(JSON_QUERY(<col>, '$._id'), ?)` (key-order insensitive) with a JSON-typed bind, and `docGetById`/`docDelete`/`docIdOf` take/return `oracle.sql.json.OracleJsonValue` instead of `String`. Scalar-`_id` views emit byte-identically to before. The etag lock composes unchanged on top. DDL gotcha: the GraphQL DDL flavor **cannot** express a nested `_id` object (ORA-24558) — a composite-key DV needs the SQL flavor (`SELECT JSON {'_id' : JSON {…}, …} FROM … WITH INSERT UPDATE DELETE`); also the server forbids changing `_id` fields on update (ORA-42603). **SOAP emission for DVs is now in** (the former v1 limitation is closed): when web services are enabled, `SAAdminWrangler.addDualityViewServiceMethods` emits `serviceDoc<Table>*` methods onto the generated `<Factory>ServiceImpl`/`Interface` — `GetAll`/`GetById` always, `Insert`/`Update`/`Delete` per the ALLOW flags — the first per-table service surface (ordinary tables are still not exposed). Documents cross SOAP as JSON **text** (`String` — SOAP can't carry `OracleJsonValue`); a composite `_id` crosses as the `_id` object's JSON text, parsed in the generated code via `OracleJsonFactory.createJsonTextValue`. The method scaffold mirrors the PL/SQL recipe (`@WebMethod`/`@WebParam` gated on target JVM, pre/post-call stubs per the WS_*_CALL_STUB flags, `CSException`→`<Factory>ServiceException` wrapping — the etag lock surfaces that way — and an `alwaysReleaseResources` finally block), and the chunks ride the same `.prc` temp-file merge: per-table `webserviceInterfaceCode`/`webserviceMethodCode` on `SingleNamespaceObject`, swept into the service classes by a new `theTables` loop in `generateWebServiceClasses`. Deliberate scope cut: the doc methods are NOT added to the external-connector method list, so the optional JSON/JSON-RPC connector layer doesn't expose them. `Propfiles/generic_test_23ai.pb2` now sets `WEB_SERVICES=YES` so the standard regen exercises the emission (92 files when this landed; the tree has grown since and `Scripts/provisioning/expected-file-counts.txt` is the current record — 181 on a 23ai-line server, with a cross-box floor of 60). Fixtures: `OB_DV_BASE`+`FIXTURE_DV` (scalar) and `OB_DV_BASE2`+`FIXTURE_DV2` (composite, two-column PK) in `sql/datatypes_23ai_gen.sql`; `Propfiles/generic_test_23ai.pb2` names both; `TGen23ai` round-trips the full document CRUD on both views plus stale-etag rejection, fresh-etag re-update, the no-`_metadata` overwrite path, and key-order-swapped/OSON-extracted composite ids, and also drives the SOAP layer end-to-end on both views (JSON-text CRUD, key-order-swapped composite ids as text, stale etag as the service exception). Harness gotcha it works around: the propfile bakes `WS_ALWAYS_RELEASE=YES` + `CLOSE/COMMIT_CONNECTIONS=YES`, which would commit and close the shared test connection after every service call — `TGen23ai` subclasses the ServiceImpl and calls the protected `setAlwaysReleaseResourcesFlag(false)`.

**Identity columns (12c+ `GENERATED ... AS IDENTITY`) are now handled.** `SAAdminWrangler` feature-detects `ALL_TAB_IDENTITY_COLS` (probe + cached flag, same recipe as `VECTOR_INFO`; pre-12c is untouched) and queries it per table (`SqlStatementDictionary.getTabIdentityColsQry` — kept a separate single-view query, NOT a join/correlated subquery, because of the 19c dictionary bind-loss issue). A **`GENERATED ALWAYS`** column is excluded from the generated INSERT column list (ORA-32795) and UPDATE SET list (ORA-32796) — it stays in every SELECT, and the WHERE clause of UPDATE/DELETE still keys on it — and `rowValidate` treats any identity column as nullable (the DB fills it). So `rowInsert` without a PK now works and `rowUpdate` no longer hits ORA-32796. **`rowInsert` also returns the database-generated key**: the generated `AbstractSqlStatement` has a `setGeneratedKeyColumn(String)`/`getGeneratedKeyValue()` hook (prepare switches to `prepareStatement(sql, new String[]{col})` — Oracle adds a RETURNING clause — and `issueCall` reads `getGeneratedKeys()`), and the Mgr's `rowInsert` sets the hook on its Ins statement and writes the key back into the row before returning (`theRow.setRowId(...)`), which also makes the post-insert LOB `rowLock` refetch work on identity-PK tables. Applies to ALWAYS and BY DEFAULT identities alike (`getGeneratedKeys` returns the stored value either way). Verified live on FREE23 (insert → returned id drives getByPk/update/delete through the generated `FIXTURE_TABLE` DAO; `TGen23ai` now covers this plus a binary-vector write via `rowUpdate`); generator output for tables without identity columns is unchanged apart from the uniform per-package `AbstractSqlStatement` template additions (verified by tree diff; the identity-*exclusion* change alone was proven byte-identical over the full generic_test1 tree).

**`TIMESTAMP` table columns now compile and round-trip (base-generator fix).** A bare `TIMESTAMP` column used to make the *whole* generated DAO factory fail — a cluster of base-generator bugs. Three sites fixed: (1) the row field is a `String` but the INSERT/UPDATE statement's date-token `setParam<Col>` group had no `String` overload → `CallableStatementParameterEngine.addDateSetMethods` now also emits `setParam<Col>(String)` (parsed via `java.sql.Timestamp.valueOf`, null-safe) — a *purely additive* overload on every date column/param (byte-diff proven: 0 lines removed); (2) `SAAdminWrangler`'s `processMany` row-read generated `new oracle.sql.TIMESTAMP((java.sql.Timestamp)theArray[N])`, but `theArray[N]` is an `oracle.sql.TIMESTAMP` → `ClassCastException` on read; now casts to `(oracle.sql.TIMESTAMP)theArray[N]` directly and binds through `setRow<Col>(oracle.sql.TIMESTAMP)`, the way `TIMESTAMPTZ`/`LTZ` already did (fires only for TIMESTAMP columns — e.g. `generic_test1`'s `LegacyDatatypes2`); (3) the MCP table path (above). The proc `TIMESTAMP` OUT path was already fine (it reads through `getParam<Cap>String()`). Verified across three Oracle lines: **12c ORCL12 277/0/2, 21c ORCL21 271/0/2 (`-Pharnesses-longids`), 23ai FREE23 281/0/2**, plus `FIXTURE_DR.a_ts` round-tripping through the generated MCP DAO. **`TIMESTAMP WITH [LOCAL] TIME ZONE` columns are now fixed too (2026-08-13), and what they actually were is worth knowing: NOT a missing feature but a GENERATION FAILURE no fixture could reach.** A table with a PRIMARY KEY and a zoned-timestamp column emitted code that **did not compile** — `ObTzProbeMgr.java: incompatible types: byte[] cannot be converted to String`, on `rowInsert` and `rowUpdate`, both TZ types. The row field is `byte[]` (Oracle's wire form, with converting accessors) but the INSERT/UPDATE setter came out `setParam<Col>(String)`, because `SqlStatementWrangler`'s comment-hint parser had no entry for the `oracle.sql.TIMESTAMPTZ`/`TIMESTAMPLTZ` spellings its own comment writer emits, and unknown hints fall back to `STRING` **with a warning the generator then exits 0 after**. Fix: both spellings are `ASP_DATA_TYPES` tokens with synonyms, placed **BEFORE the RAW block on purpose** — the field is a `byte[]`, so anything reaching the `byte[]` synonym would bind it RAW, the same ambiguity binary `VECTOR` needed its own token to escape. The engine's emission was correct all along and simply unreachable: it now binds `new oracle.sql.TIMESTAMPTZ(<param>)` → `setTIMESTAMPTZ`. **Why six green boxes never saw it:** the only fixture table with live TZ columns (`SCALAR_DATATYPES_2`) has **no primary key**, so no Ins/Upd is emitted and the tree compiles; and `LEGACY_DATATYPES_2` has its TZ columns **commented out** in the DDL. Verified by a scratch PK'd table: 4 errors → 0, and a live round trip preserving `2019-03-01 14:25:36.123 Asia/Calcutta` and the LTZ. `generic_test1` is byte-identical (2459 files), so no existing config moves. **Still open: no committed propfile has a PK'd TZ table**, so nothing guards this — that fixture gap is the real root cause and it will come back without one.

**Driver hazard, NOT ours and NOT fixable here: `new oracle.sql.TIMESTAMPTZ(Connection, String)` SILENTLY DISCARDS A NUMERIC UTC OFFSET.** `"2019-03-01 14:25:36.123 +05:30"` comes back as `2019-03-01 14:25:36.123 GMT` — the wall-clock is kept and the instant moves by 5½ hours. A region name (`Asia/Calcutta`) round-trips correctly, no-space `…123+05:30` throws `NumberFormatException`, and the database's own `to_timestamp_tz` handles the offset fine. The generated `setRow<Col>(java.sql.Connection, String)` delegates straight to that constructor, so it inherits the behaviour. **Prefer the `oracle.sql.TIMESTAMPTZ` / `byte[]` setters for anything where the instant matters**; the `byte[]` path is Oracle's own representation and is lossless. (INTERVAL OUT params were a sibling base bug — the SOAP `ServiceImpl` OUT-unload read the object getter into a String field — fixed separately by giving the INTERVAL-datatype case in that switch the `getParam<Cap>String()` variant, mirroring TIMESTAMP; verified 12c/21c/23ai, byte-identical for the canonical set.)

## Session identification (`DBMS_APPLICATION_INFO`)

Every Oracle connection this project opens now names itself, by calling
`DBMS_APPLICATION_INFO.SET_MODULE` once, immediately after login. Shared helper:
**`com.mcpdbwizard.pub.SessionInfo`** — in `pub` because both halves need it, the same reason
`EnvironmentSecret` lives there.

- **The generator's own connection** (`ConnectionWrangler.connect`, inside the existing
  `instanceof OracleConnection` block, next to `ALTER SESSION DISABLE PARALLEL QUERY`) reports
  module **`MCPDBWizard`**, action **`Introspect`**. That covers the Swing UI, batch mode *and* the
  web Design page, which all reach Oracle through this one method.
- **Generated code** reports the **DAO factory class name** as its module, set in
  `confirmConnection(String)` inside the existing `if (!oracleVersion.startsWith("DB2"))` block — so
  it applies to all four connection types (hand-coded, JNDI, DataSource, JBO) rather than only the
  direct one. Action is left null: at connect time nothing is happening yet. The emitted field is
  `oracleModuleName`, with `setModuleName`/`getModuleName`, mirroring the existing
  `oracleTimeZoneName` pattern exactly — set it before the first call that needs a connection, since
  changing it afterwards does not rename a session already open. Empty or null skips the call.

**Why it matters more here than in an ordinary application.** A generated DAO layer is deliberately
a service-account shape — every caller is the same Oracle user, which `docs/mcp-security-review.md`
records as accepted — so the username identifies nobody. `MODULE` is the first column a DBA groups
by when a session is blocking, burning CPU or holding a lock, and it is what `DBMS_MONITOR` and AWR
key their per-module aggregates on.

**Failure is logged and ignored, never fatal**, at both sites. `DBMS_APPLICATION_INFO` is granted to
`PUBLIC` on a stock install, so a failure means someone revoked it deliberately and their
application should still run. `SessionInfo.setModule` throws and each caller absorbs it, rather than
the helper swallowing it silently.

**The module must not be a token — but `Namer.param_prod_name` is no longer one** (corrected
2026-08-11; this paragraph previously asserted the opposite as current fact). It once held
`SUBST_PROD_NAME`, from a `sed` step that no longer runs, and putting it in `V$SESSION` would have
published exactly that string. The MCPDBWizard rename **inlined it**: it is now the plain literal
`"MCPDBWizard"`, so `SessionInfo.GENERATOR_MODULE` referencing it is correct and the value reaching
`V$SESSION` is right. What survives is the *rule*, and the test that enforces it —
`SessionInfoTest` asserts the module contains no `SUBST_`, which is the check that matters however
the constant is spelled. Verify the constant before repeating either claim; the whole `Namer` family
was inlined at once, so a nearby `param_*` is unlikely to still be a token either.

**Lengths:** Oracle truncates `module_name` at 48 bytes and `action_name` at 32, silently.
`SessionInfo` truncates first so a long name is clipped where we said it would be. The cut is by
character, so a multi-byte name can still be clipped further by Oracle — harmless for what are ASCII
class names in practice.

**This changes emitted output for every config** (the factory gains a field, two methods and the
call), so byte-identity with pre-change trees is intentionally broken. File counts do not move.
Tests: `SessionInfoTest` (db-free — truncation, the null guards) and `SessionInfoLiveTest` (gated;
reads the values back through `SYS_CONTEXT('USERENV', 'MODULE'/'ACTION')` rather than `V$SESSION`,
which needs a grant an application account often lacks).

**`DBMS_APPLICATION_INFO` is called ONCE, when the connection is created — a decision, not an
omission (2026-08-04).** Per-call `SET_ACTION` in the MCP server's `call(...)` funnel was considered
and **rejected**: the funnel does know the tool name, but labelling each call costs **two extra
round trips** (set, then clear in a `finally`) on every tool invocation, and the tool identity is
already recorded where it belongs — the `MCP-CALL` log line and the audit sink. `ACTION` therefore
stays null. So `SessionInfo` has no `setAction`, and the funnel is untouched. If per-call labelling
is ever wanted, the mechanism to use is **not** `DBMS_APPLICATION_INFO` but
`connection.setClientInfo("OCSID.ACTION", …)`, which Oracle piggybacks onto the next round trip and
so costs nothing extra — that is the only form that respects the decision above.

## The extra Oracle TYPE objects (`extraObjects.sql`), and the two checks on them

JDBC cannot pass an array of PL/SQL records into a PL/SQL package array parameter — the only array
form that crosses is one built on real SQL types. So under **`EXTRA_SQL=YES`** (the Swing "Create
needed TYPE objects" checkbox) the generator invents an `_T` object type and an `_A` collection type
per record shape, and delivers them **twice**: as DDL in `extraObjects.sql` beside the DAO factory,
and as `createExtraTypeObjects()` on the generated `ServiceImpl`, which issues the same statements
over JDBC. The emitted MCP server calls that method at start-up when a routine it exposes has a
collection param (`haveCollectionProcs`). Names are the config's `DEFAULT_TEMP_PREFIX` plus a short
discriminator — `OSOFT_T`, `OSOFTN_A`.

**ORA-2303 is the ORDINARY outcome, not an error, and that is the whole difficulty.** The `_A`
collection is a dependent of the `_T` object type, so from the second run onwards `CREATE OR REPLACE`
on the object type can never succeed — measured on 26ai: run 1 creates, run 2 with identical DDL
raises ORA-2303. The generated code has always tolerated that code, correctly. **But a type whose
SHAPE HAS CHANGED fails identically** (verified: a third run with an extra column also raises 2303,
and `USER_TYPE_ATTRS` still shows the old attributes), leaving the stale definition in place while
the program binds against it. So "make ORA-2303 loud" is exactly wrong — it would warn on every
restart and still not name the fault.

**Stale is detected by comparing against `USER_SOURCE`** (added 2026-08-11, `99a60df`). The emitted
`executeImmediate` now returns whether the DDL actually ran; when it did not, `confirmExtraTypeMatches`
reads the stored specification and compares. Match → quiet; differ → both definitions logged and a
`CSException` thrown, because continuing binds the wrong values. **`USER_SOURCE` rather than
`USER_TYPE_ATTRS` is the load-bearing choice:** Oracle stores a type's specification text verbatim
(true for collection types too, including the trailing `;` the generator sends), so no mapping from
the DDL's datatype spellings onto the dictionary's is needed — that mapping is where a comparison
would spend its effort and earn false alarms, and a startup check people learn to ignore is worse
than none. The comparison itself is **`SqlUtils.normaliseTypeSpec`**, in the runtime library rather
than emitted so it can be unit-tested; it must equate three spellings of one type — one concatenated
line from generated Java, several lines from `extraObjects.sql`, and Oracle's own form.

**Missing is reported by the web Runtime page**, via `mcpdbwizard-web`'s `ExtraTypeCheck`: it reads
`extraObjects.sql` from the generated tree and names the types the schema lacks. It runs **after** the
server is up, because the server creates them itself when a tool needs one — checking earlier reports
everything missing on a first run — and it reports rather than blocks, since only collection params
are affected. **It asks `USER_TYPES`, never `ALL_TYPES`:** these names collide across schemas as a
matter of course (four schemas on the test estate each own an `OSOFT_T`), so an unscoped query matches
a stranger's type and pronounces every type present when none exists — a check that can only say
"fine". That was a real bug, caught only by running it against a live box.

**Known pre-existing defect, deliberately not fixed:** a record with no attributes emits
`CREATE OR REPLACE TYPE <x>_T AS OBJECT` with no attribute list, into both deliveries
(`generic_test1` does this). Oracle **accepts** the statement and leaves an **INVALID** type rather
than rejecting it, which is why it has never surfaced. Fixing it means deciding what an
attribute-less record should mean.

## MCP server generation (Model Context Protocol)

**Operator-facing deployment guide: [`DEPLOYMENT.md`](../DEPLOYMENT.md) at the repo root.** It covers the process shape (web app on 8080; the generated MCP servers on 8090–8109, several at once, loopback-only and reached through the web app's `/mcp/<config>` proxy), the **generation-time flag vs runtime environment variable** distinction that catches people out (`MCP_HTTP_TOKEN` is *both* — a config flag that emits the filter, and the env var carrying the secret), every knob below in one table, and a symptom→cause table for the `exit 2` refusals. Keep it in step when any of the flags or guards here change.

**Where the web app's accounts sit relative to generation-time curation (read before assuming either replaces the other).** The `mcpdbwizard-web` module now has many accounts and an access matrix deciding which of them may drive which config, enforced by its `/mcp/<config>` proxy — the only component that knows who is calling, since a generated server connects as one shared Oracle user and sees a single bearer token that is a door key rather than an identity. **That layer governs whole configs, never individual tools, and it does not change anything in this file.** Tool-level authorization is still the config: an object that is not selected has no code emitted for it and cannot be reached, which stays the stronger guarantee because it is enforced by absence from the binary rather than by a running process. So two groups needing different tools over one schema is still **two configs**, exactly as before — the matrix is what stops each group reaching the other's, which previously nothing did. A generated server is unchanged by any of this; it does not know the proxy exists.


The generator can emit a **standalone MCP server** (`<Factory>McpServer.java`) that exposes the generated code as MCP tools, so an LLM/agent can drive the schema directly. It is gated by the **`MCP_SERVER=YES`** propfile flag (the "Create MCP Server Class" GUI checkbox, `ApplicationShell.mcpServerFlag` → `SAAdminWrangler.generateMcpServerClass`) and requires **`TARGET_JVM` ≥ 17** (the MCP SDK, `io.modelcontextprotocol.sdk:mcp` 2.0.0, an `<optional>` pom dep, needs Java 17+; nothing is emitted below that). The server logs through `com.mcpdbwizard.pub.JulLog` (java.util.logging → stderr) because on the stdio transport **stdout carries the protocol frames**; tool handlers share one lock (one `Connection` per factory) and every handler runs through a common `call(...)` that maps `CSDocumentChangedException` → an isError "re-read and retry" result and other `CSException`s → an isError database-error result. **Two transports, chosen at runtime:** default **stdio**, or the MCP **Streamable HTTP** transport when run with args `http [port]` (default 8080) — the same tool list (built once as a `List<SyncToolSpecification>`) is served either way; only the transport provider and the blocking loop differ. The HTTP mode hosts the SDK's `HttpServletStreamableServerTransportProvider` (an `HttpServlet`) in an embedded **Jetty 12** (`org.eclipse.jetty.ee10:jetty-ee10-servlet` + `jakarta.servlet-api` 6.1, both `<optional>` pom deps) at `http://<host>:<port>/mcp`. The generated server *compiles* against Jetty; a *stdio* run never loads the Jetty classes (they're only referenced in the untaken `http` branch), so stdio deployments don't need the Jetty jars at runtime. **Optional HTTP bearer-token auth** is gated by the **`MCP_HTTP_TOKEN=YES`** propfile flag (`ApplicationShell.mcpHttpTokenFlag`, propfile-only — no GUI control; a modeled `Schema` scalar so it round-trips through `.json` too). When set, the generated `http` branch reads the actual secret from the **`MCP_HTTP_TOKEN` environment variable** at run time (never baked into the source) and installs a `jakarta.servlet.Filter` on `/mcp/*` that 401s any request whose `Authorization: Bearer <token>` header does not match (constant-time `MessageDigest.isEqual` compare); if the env var is unset/empty the server logs an error and `System.exit(2)`s rather than serving unauthenticated (fail-closed). The default (flag absent/`NO`) emits no auth code — byte-identical to before. stdio is unaffected (auth is HTTP-only; stdio security is process-level). `Propfiles/generic_test_23ai.pb2` sets `MCP_HTTP_TOKEN=YES` so the standard regen compiles the auth branch; verified end-to-end on FREE26 (no header → 401, wrong token → 401, correct token → 200; missing env var → exit 2). **Optional TLS/HTTPS** is gated by the **`MCP_HTTPS=YES`** propfile flag (`ApplicationShell.mcpHttpsFlag`, propfile-only — no GUI control; a modeled `Schema` scalar). When set, the generated `http` branch builds the Jetty server with **no default plaintext connector** (`new Server()`) and adds an SSL `ServerConnector` (`SslContextFactory.Server` + `SslConnectionFactory` + an `HttpConnectionFactory` with a `SecureRequestCustomizer`) on the chosen port, so the endpoint is `https://<host>:<port>/mcp`. The keystore path and passwords come from the **`MCP_TLS_KEYSTORE` / `MCP_TLS_KEYSTORE_PASSWORD`** (and optional **`MCP_TLS_KEY_PASSWORD`**) environment variables at run time (never baked in); if the keystore is unset/missing the server logs and `System.exit(2)`s (fail-closed). No new pom dependency — the TLS classes are transitive via `jetty-ee10-servlet` (`jetty-server` + `jetty-util`). TLS and the bearer token are **independent and composable** (both can be on: token = access control, TLS = wire encryption). `Propfiles/generic_test_23ai.pb2` sets `MCP_HTTPS=YES` (alongside `MCP_HTTP_TOKEN=YES`) so regen compiles the TLS branch; verified end-to-end on FREE26 (https + correct token → 200, no/wrong token → 401 over TLS, plaintext to the TLS port → connection fails, cert verified without `-k`, missing keystore env → exit 2). This closes options **#1 (bearer token) and #2 (TLS)** of the MCP-auth gap; a read-only/curated tool mode is a deliberate WON'T-DO.

**`--list-tools`: what this server exposes, without running it (2026-08-24).** Run a generated server with that single argument and it prints the `tools/list` payload a client would receive — every tool name, description and `inputSchema` — and exits. **It connects to nothing.** The check sits at the very top of the emitted `main`, ahead of the factory/pool construction, which is what makes it answerable before the database is reachable and for a server that compiled and then failed to start: a tool spec is a name, a description and a schema baked in at generation time, and only its call handler ever reaches Oracle. It is the *server's own* answer, serialized through the same `JacksonMcpJsonMapper` the transport uses, rather than anything re-derived from the config — a second derivation would be free to drift from the thing that actually answers. **This is why the tool-list string is now built above `main` in `generateMcpServerClass`** (that loop concatenates and emits nothing, so hoisting it changed no generated source). The web console runs it after every generation, caches the output as `tools.json` in the config's workspace, and renders it in **two places, deliberately**: at the foot of the **Service Options** tab with a stale mark when the config has been edited since, and **per server on the Runtime page**, where it needs no such mark because every row there IS a built server. The Runtime copy is collapsed and carries names and arguments only — that page holds up to twenty servers at once, so the schemas stay in the download — while the Design copy opens by default. Both read the one cached file and share one cap (`McpToolListing.MAX_INLINE_JSON`), which lives on the listing rather than on either page so the two cannot drift — see `RuntimeManager.writeToolListing` and `web/…/config/McpToolListing.java`. **`RUN_ON_START` needs its own call and now has one** (`adoptToolListing`): that path deliberately does not regenerate, so it never reaches the step that writes the listing, and a restarted container showed "never generated" on the tab while a server for that config was running — it also left the Runtime page's tool count at 0, which reads as "exposes nothing" rather than "nobody counted". It asks only when the cached listing is missing or older than the jar, since the jar that answered is the jar being launched. **Gotcha, and the FIRST FIX FOR IT WAS WRONG — worth reading before touching that spawn.** A server built by an older generator does not know the argument and falls through to the stdio transport. Closing the child's stdin looks like the cure and is NOT: measured on a real workspace, such a server does **not** exit on EOF — the emitted stdio branch keeps the JVM alive on purpose — so it ran the full 60-second timeout anyway, and on the way it opened an Oracle session and started a Kafka producer. What actually works is not spawning it: `jarSupportsToolListing` reads the emitted `*McpServer.class` out of the jar and looks for the literal `--list-tools`, refusing **only on positive evidence of absence** (a file that cannot be read as a jar is still attempted, since "I could not tell" is a different answer). The marker is read from the CLASS rather than from `build.properties`, because the jars that need catching are exactly the ones written before any fingerprint said anything about this. **The panel is CAPPED at 100KB of JSON** (`OptionsController.MAX_INLINE_TOOL_JSON`), over which the per-tool schemas AND the whole payload both move to a `/design/tools.json` download and the table keeps name, arguments and description. **Capping only the payload would have fixed half of it:** each schema is in the page twice, once in its tool's row and once in the payload below. Measured on `generic_test1_mcp` (573 tools): 700KB of payload plus 756KB of per-tool schemas plus 255KB of table = **1.7MB of page, down to 255KB**. The oversize case renders NO schema rather than a truncated one — a cut JSON document is not one, and somebody would copy it. The download takes no config name, so it cannot be pointed at a config the caller may not open. Db-free coverage: `GeneratedMcpToolListingShapeTest` (app), `McpToolListingTest`, the `RuntimeManagerTest` set for the spawn outcomes and the jar-marker guard, and `ServiceOptionsToolListingRenderTest` for the page in both sizes.

Surfaces exposed as tools (each with a JSON-schema `inputSchema` built from the generator's datatype metadata; JSON-crossable types are native `JSON` → object, dense `VECTOR` (`double[]`) → array, `DATE` (`java.util.Date`) → ISO-8601 string (`yyyy-MM-dd'T'HH:mm:ss`, via generated `formatIsoDate`/`parseIsoDate`), `RAW`/binary `VECTOR` (`byte[]`) → base64 string, `ROWID`/`UROWID`/`TIMESTAMP`/`INTERVAL` (PL/SQL params) → string, an OUT/return **ref cursor** → JSON array of row objects (via `refCursorToJson`), **CLOB**/**BLOB** PL/SQL params → text / base64 string (via the wrapper's LOB accessors), a flat **PL/SQL record** or **SQL OBJECT type** param → JSON object (via the field-based `RECORD_MAPPER`), a **PL/SQL collection** of NUMBER/VARCHAR2/DATE/RAW/record/object → JSON array (via `PlsqlArray`), and scalars — number/string/boolean; the type→JSON mapping lives in the shared `mcpJavaSchemaType`/`mcpArgConversion`/`mcpValueToJsonExpr` helpers keyed on the Java type, so every surface picks a new crossable type up at once. Still uncrossable: an IN ref cursor (no way to construct one client-side), collection elements outside NUMBER/VARCHAR2/DATE/RAW/record/object (e.g. nested collections, BOOLEAN), FLOAT16 vectors (server-blocked, `ORA-51802`), and — over MCP only — the binary/sparse format of a VECTOR *proc param* (a VECTOR proc tool crosses dense-array only; VECTOR table columns get the full dense/binary/sparse crossing):
- **JSON-relational duality views** — document CRUD (`<view>_doc_get_all/_get_by_id/_insert/_update/_delete`, per the ALLOW flags), with the etag optimistic lock surfaced as an isError result, composite-`_id` objects, a `maxDocuments` cap on get-all, and each view's field list baked into the tool schemas from `ALL_JSON_DUALITY_VIEW_TAB_COLS`.
- **Ordinary tables** — row CRUD by PK (`<table>_get_by_pk/_insert/_update/_delete`); rows cross as JSON objects keyed by lower-cased column name via two generated helpers (`<base>RowToJson` / `<base>RowFromDoc`). A `GENERATED ALWAYS` identity is dropped from the insert schema (DB assigns it, inserted row returned); `update` is a full-row replace; a non-key column of an unsupported type is omitted (a table with a non-crossable *PK* or no PK is skipped entirely). **Long-identifier tables** (Oracle name > 30 chars, legal on 12.2+) are exposed like any other — the generator emits their class names un-hashed and the tool metadata derives from the same fixed Java name, so the calls match the generated DAO exactly (`TGen23aiMcp` covers one end-to-end). **CLOB/BLOB** columns are supported (CLOB → JSON text, BLOB → base64): read direct from the row's public LOB locator (`getByPk` keeps it live), write file-based (`RowFromDoc` writes a temp file and calls the `setRow<Col>(File)` setter, since `rowInsert` streams a file into the LOB); BFILE stays unsupported. **DATE** columns cross as ISO strings and **RAW**/binary-`VECTOR` columns as base64 (so `FIXTURE_TABLE`'s `bin_embed` binary vector, formerly omitted, now crosses). A bare **`TIMESTAMP`** column crosses as a plain string in Oracle's `"yyyy-mm-dd hh:mm:ss.fff"` form: its generated row field is a `String`, so `buildTableMcpInfo` types it `String` and reads it through the `getRow<Col>String()` variant (the plain `getRow<Col>()` returns a `java.sql.Timestamp`). This rides a **base-generator fix** that made TIMESTAMP columns work at all — see "TIMESTAMP table columns" below. TZ timestamps are still omitted.
- **Table secondary lookups** — unique-key (`getByUk*`, via the row overload → single row), index (`getChildByIx*`, via the scalar-arg overload → single row for a unique index, array otherwise), and **foreign-key child** (`getChildByFk*` on the parent → the *child* table's row array, serialized by the child's own helper, emitted only when the child table is also exposed). Method name/kind/cardinality are **captured during the constraint-generation loop** (not re-derived) onto `SingleNamespaceObject.mcpTableLookups`; columns are resolved in `buildTableMcpInfo`.
- **PL/SQL procedures/functions** — drive the generated callable-statement **wrapper directly** through the factory (`get<Class>PlSqlDAO()`): set every IN / IN OUT param, `executeProc()`, then read the function return and **every** OUT / IN OUT param, returned as a JSON object keyed by parameter name (function return under `"result"`). So **any number of OUT / IN OUT params** comes back (the product goal — call any procedure regardless of inputs/outputs). Needs **no WEB_SERVICES** (the wrapper is always generated); the full param list is captured from the engine during wrapper generation (`SingleNamespaceObject.mcpProcParams`, `CallableStatementParameterEngine.getMcpParamTuples()`). Argument/output keys are the Oracle parameter names (lower-cased). `DATE` params cross as ISO strings, `RAW` as base64, and `ROWID`/`UROWID`/`TIMESTAMP`/`INTERVAL` as strings — the last group reads/writes through the wrapper's `getParam<Cap>String()`/`setParam<Cap>(String)` accessors (the plain `getParam<Cap>()` returns a typed object or doesn't exist), so `getMcpParamTuples()` also carries each param's Oracle datatype constant and `mcpProcUsesStringAccessor` keys off it (UROWID/TIMESTAMP both report javaType `"String"`, indistinguishable from VARCHAR2 otherwise). INTERVAL additionally needed a base **SOAP ServiceImpl** fix — its OUT-unload switch had no INTERVAL case, so an INTERVAL OUT param fell to the default (the object getter) and would not compile into a `String` field; it now reads the `getParam<Cap>String()` variant, mirroring the TIMESTAMP case (byte-identical for the canonical set; verified 12c/21c/23ai). An **OUT (or function-return) ref cursor** crosses as a JSON array of row objects — the wrapper exposes it as a `com.mcpdbwizard.pub.ReadOnlyRowSet`, serialized generically by the emitted `refCursorToJson` helper (keys lower-cased, DATE columns ISO, others via Jackson); an *IN* ref cursor still disqualifies (no way to construct one client-side). **CLOB**/**BLOB** params cross as text / base64: a CLOB IN binds through the `setParam<Cap>(String)` overload and reads via `getParam<Cap>Clob()` (`clobToJson`), a BLOB IN via `setParam<Cap>(byte[])` and `getParam<Cap>Blob()` (`blobToJson`) — CLOB vs BLOB keys off the captured Oracle datatype (a function-return LOB is left out, its accessor naming differs). **OUT-getter naming was bug D (fixed 2026-08-05, `0337a75`), and both halves are traps worth keeping.** (a) `SqlUtils` maps **NCLOB** onto `ORACLE_CLOB_DATATYPE` deliberately (`oracle.sql.NCLOB` extends `CLOB`, and `LongObjectLoader` has no `loadNCLOB`), so the numeric type cannot tell them apart — yet the engine still names the accessor `getParam<Cap>Nclob()`. `getMcpParamTuples` therefore carries the **raw Oracle type name** as an 8th field (every existing reader is length-guarded, so the addition was safe). (b) **Legacy and native BOOLEAN are generated differently**, and the same APPSCHEMA procedure shows both: on 12c/18c/19c/21c the dictionary says `'PL/SQL BOOLEAN'` → `ORACLE_BOOLEAN_DATATYPE` → the wrapper emits `…BooleanObj()` and `…Boolean()` with **no bare getter**, while on 23ai/26ai it says `'BOOLEAN'` → `ORACLE_NATIVE_BOOLEAN_DATATYPE` → a plain `getParam<Cap>()` returning `Boolean`. So `mcpProcUsesBooleanObjAccessor` covers the **legacy type only**; covering both (on the assumption they are named alike) emitted `getParamPBooleanBooleanObj()` against a class holding only `getParamPBoolean()` and took FREE26 from 8 errors to 66. **Verify any accessor-naming change on BOTH Oracle lines** — the 23ai line's plain getter genuinely exists, so a break there can be invisible. A flat **PL/SQL record** or **SQL OBJECT type** param crosses as a JSON object: both hold their values in public fields, which the wrapper binds field-by-field (an object param is flattened to per-attribute binds, *not* a STRUCT/`toDatum`), so an emitted field-visibility Jackson mapper (`RECORD_MAPPER`) round-trips them — IN via `convertValue(arg, <Class>.class)` passed to the wrapper's `set<Cap>(...)` **setter**, OUT via `writeValueAsString`. **Two different fields, and only the first is reliably public (bug F, fixed 2026-08-05 in `ae7e7ee`).** The *record class's own* attributes are public — that is what `RECORD_MAPPER` needs and it holds generally. The **wrapper's field holding the record** is a separate thing and is NOT always public: `generic_testg`'s `RedlineTestPkgTest` declares `protected RedlineTest paramData` beside a public `setParamData(...)`/`getParamData()` pair, and `generic_testg`'s SDO wrappers do the same. The emitter used to reach past those accessors and touch the field directly (`theProc.paramData = RECORD_MAPPER.convertValue(...)`), so `generic_testg_mcp` failed to compile with `paramData has protected access` — 12 errors per regen on every box. It now emits the accessors, which already existed; **do not "simplify" either end back to a field assignment**, because the public-field assumption was only ever true of `generic_test_23ai`'s fixture, the one propfile that used to emit an MCP server. Keys are the Java field names (`param<Field>`), plus a `recordName` metadata field (ignored on input); Jackson recurses for nesting, and the base generator now synthesizes *nested* record types too (a record-in-record field gets its own populated class — see the nested-records work below), so record-in-record params cross as nested JSON objects. Gated by `mcpIsRecord`: `ORACLE_ROWTYPE_DATATYPE`/`ORACLE_OBJECT_DATATYPE` + a non-`Object` class. A **PL/SQL collection** (VARRAY / nested table / index-by) of NUMBER or VARCHAR2 crosses as a JSON array through `PlsqlArray`'s generic `getCurrentValuesAsObject`/`setNewValuesAsObject` (OUT via `collectionToJson`, IN via `toScalarObjectArray` → a `new <Coll>(COLL_LOG)` bound with `setNewValuesAsObject`; **a scalar index-by table is the exception, and it was bugs B and C — one wrong assumption at three call sites, fixed 2026-08-05 in `ae7e7ee`** — the wrapper types it `com.mcpdbwizard.pub.PlsqlIndexByTable2`, a *runtime-library* class, so it must NOT be package-prefixed (`<package>.plsql.com.mcpdbwizard.pub.…`, 72 errors) and is constructed `new …(oracle.jdbc.OracleTypes.NUMBER, 0)` from the element's Oracle type code rather than from a log. That code is load-bearing — the class decides element by element whether a value is a `String` or a `BigDecimal` purely from it, so a convenience `(LogInterface)` overload would have traded a compile error for a silent wrong-type bind. `PlsqlIndexByTable2` was also made to implement `PlsqlArray`, which `collectionToJson` takes: purely additive over the existing `getArray()`/`setArray(Object[])`, so programs already linking it are unaffected); the element type is looked up from `ALL_PLSQL_COLL_TYPES`/`ALL_COLL_TYPES` in `getMcpParamTuples` (`ALL_ARGUMENTS` doesn't expand a package collection type into an element row) and carried as the tuple's 7th field. A collection of a **record / SQL object** element crosses as a JSON array of objects: OUT serializes each element through `RECORD_MAPPER` (`recordCollectionToJson`), IN builds the element instances with `RECORD_MAPPER.convertValue` into the collection's element class — resolved at runtime by reflecting the collection's `theArray` field generic type (`toRecordObjectArray`) — which the collection's `setNewValuesAsObject` accepts directly (it has an `instanceof <ElementClass>` branch, and the wrapper's per-element `toDatum` reads the object's public fields). A PL/SQL **package array** binds through generated SQL shadow types, so a collection param **requires BOTH `WEB_SERVICES` AND `EXTRA_SQL`** (the server calls `theServiceImpl.createExtraTypeObjects()` at startup) and `needServiceImpl` includes `haveCollectionProcs`. **Both, not either:** `WEB_SERVICES` is what emits the `ServiceImpl` class, but `EXTRA_SQL` — the "Create needed TYPE objects" flag — is what puts `createExtraTypeObjects()` *inside* it (`ExtraTypeWrangler.addCreateMissingTypeObjectsMethod` runs only under that flag). `mcpProcUnsupportedReason` checked only the first until 2026-08-05, so a config with `WEB_SERVICES=YES, EXTRA_SQL=NO` and a collection proc emitted a server calling a method that was never written — generation reported success and `javac` then failed with `cannot find symbol: createExtraTypeObjects()`. A **DATE** element collection crosses as an array of ISO strings and a **RAW** element as base64 (element kinds `date`/`raw` in `mcpCollectionElementKind`; `collectionToJson` ISO-formats `Date` elements per element, `toScalarObjectArray` parses ISO→`Date` and base64→`byte[]` on the way in — the collection classes accept `java.util.Date`/`byte[]` directly). **An index-by table takes the same Oracle types by a DIFFERENT ROUTE, and the difference is the element KIND rather than the range:** `PlsqlIndexByTable2` is genuinely binary (every branch reads `== VARCHAR`, with numeric the only alternative), so it cannot hold the `java.util.Date` or `byte[]` a generated collection class takes. `mcpCollectionElementKind` therefore answers **per container**, giving an index-by table its own TEXT kinds — `datetext`, `timestamptext`, `timestamptz` and `rawhex` — each riding the VARCHAR slot and converted to the spelling the emitted anonymous block expects (`TO_DATE`/`TO_CHAR` for a date, `HEXTORAW`/`RAWTOHEX` for a RAW, in `McpDates` and `McpBinary` where they are unit-tested). **Do not reshape the shared kind to serve both**: reusing `date` hands `setArray` a `java.util.Date` and throws "Cannot format given Object as a Number" at run time, which looks right at the emitter and fails in the field. All three were **rejected** by `mcpProcUnsupportedReason` until 2026-08-21 (zoned) and 2026-08-26 (DATE, unzoned TIMESTAMP, then RAW); what is still rejected is an element kind the class genuinely cannot hold, today meaning a **record**. A routine is skipped unless every top-level param and the return are JSON-crossable; what still disqualifies it: an **IN ref cursor**, a **collection** whose element type is unsupported (outside NUMBER/VARCHAR2/DATE/RAW/record/object — a collection param also needs WEB_SERVICES), or a param whose type has no JSON mapping (e.g. `SDO_GEOMETRY`, FLOAT16 vectors). BFILE, LONG/LONG RAW, XMLTYPE, TZ timestamps and INTERVAL all cross now (see above) — the old "TZ trips the base SOAP bug" note was wrong (TZ params cross via the connection-taking `getParam<Cap>String(conn)` accessor).
- **User SQL statements** — call the generated **SOAP `serviceSql*` method** on a shared `ServiceImpl`, so these DO need **`WEB_SERVICES=YES`**. (**Naming trap, and it has already cost a bug:** these are the `SQL_FILENAME_<i>` keys. The propfile key **`EXTRA_SQL` is NOT this feature** — it is the Swing "Create needed TYPE objects" checkbox, and the two are completely independent: `generic_test5`/`test6` carry 29 SQL statements with `EXTRA_SQL=NO`, while `generic_test_23ai` has none with `EXTRA_SQL=YES`. This file used to call `EXTRA_SQL` the user-SQL-statement flag, and `mcpdbwizard-web` believed it — `WorkingConfig.applySqlSelection` set `EXTRA_SQL` from whether any SQL file was selected, so every web-authored config with no SQL files turned the TYPE objects off and any collection param broke.) A query returns its `CursorAttr[]` rows as a JSON array (serialized generically from the row's public fields); a DML statement returns `{"executed":true}`.
- **Sequences** — `<sequence>_nextval` tools calling `get<Seq>SequenceDAO().getNext()` (no params, no WEB_SERVICES; non-read-only).

**Tool annotations are emitted ONLY where the generator wrote the SQL itself** — table CRUD, the unique-key/index/FK lookups, duality-view doc operations and the sequence. Read tools set `readOnlyHint(true)`, mutating ones `readOnlyHint(false)`/`destructiveHint`. **PL/SQL routines and `EXTRA_SQL` statements get NO annotation at all** (2026-08-04): you cannot tell whether a PL/SQL call writes — the same fact that makes a read-only master switch a WON'T DO — and the EXTRA_SQL hint was worse, deciding `readOnlyHint` from whether the generated method returns non-void, so a `DELETE … RETURNING` was advertised as read-only while `EXTRA_SQL` is exposed as written, DDL included. This is a safety matter, not tidiness: MCP clients use `readOnlyHint` to decide whether to auto-approve a call without asking the user, so a wrong `true` can cause a silent write. **Absent and `false` are both safe; only a wrong `true` is dangerous** — which is why the truthful hints are kept rather than removed wholesale. Everything is driven by `SAAdminWrangler.generateMcpServerClass` + per-surface `add*McpTool(s)` helpers and the `TableMcpInfo`/`DualityViewMcpInfo` metadata classes. **Deliberately NOT exposed:** a generic table get-all/query tool (user SQL statements cover that), `rowLock`, sequence `currval`, BFILE columns, and the JSON/JSON-RPC connector layer. **Curation.** The config file is the curation: an object that is not selected has no code generated for it, so it cannot be reached — configs are authored by whoever runs the generator, never by an end user or the agent. A per-object "expose?" flag is therefore only worth adding where **one config entry yields several tools**, which is why **`TABLE_MCP_CRUD_<i>`** exists and why sequence / SQL-statement flags were deliberately rejected (one entry → one tool; omitting the entry already says it). `TABLE_MCP_CRUD_<i>` selects a table's row operations as letters — `C` insert · `R` `get_by_pk` **and** the unique-key/index/FK-child lookups · `U` update · `D` delete; an **absent key means all four**, so pre-existing configs are byte-identical, and a present-but-empty value drops the table entirely. **The WEB GUI's default is different, and deliberately so: a table it has not seen before renders with READ ticked only** (`WorkingConfig.NEW_TABLE_CRUD`), so saving it writes an explicit `TABLE_MCP_CRUD_<i>=R` rather than leaving the key out — insert, update and delete are never handed to an agent without someone clicking them. The config *format* is unchanged; only what the GUI pre-ticks moved, because "absent means all four" cannot be altered without silently dropping tools from every config written before it. Guarded by `NewTableIsReadOnlyByDefaultTest`, which renders the real template and asserts the three writing boxes come back unchecked. Curation is applied **at generation time** — an unexposed operation has no tool-spec method emitted at all, so it is absent from the binary rather than merely unregistered — and the emission gate mirrors the duality-view loop immediately above it, which already gates `DocInsert`/`DocUpdate`/`DocDelete` on the view's ALLOW flags. Plumbing: `Schema`/`Table` (so it round-trips through `.json`), `TableTableDataModel.get/setMcpCrud` (carried keyed on owner/name, because the index is reassigned on every save), `SingleNamespaceObject.mcpCrud`, `TableMcpInfo.applyCrudFlags`/`isFullySuppressed`. **Gotcha:** a foreign-key child lookup lives on the *parent* but returns the *child's* rows, so `exposedMethodBases` admits only **readable** children — otherwise curating a child read-off would still surface its rows through the parent's tool. Note this cuts the other way for `EXTRA_SQL`: a selected statement is exposed as written, destructive DML and DDL included, and that is BY DESIGN — one entry yields one tool, so declining to select it is the control, exactly as for sequences. A **read-only master switch is a WON'T DO** — you cannot tell whether a PL/SQL procedure writes (nothing in `ALL_ARGUMENTS`/`ALL_OBJECTS` says so, and the generator never parses bodies), so such a switch could only filter the structurally-knowable surfaces (table `insert`/`update`/`delete`, the duality-view doc writes, sequence `_nextval`) while every exposed procedure stayed callable and free to write — a switch that reads as a safety guarantee and is not one. For the same reason the emitted `readOnlyHint`/`destructiveHint` annotations are advisory client metadata, not enforcement. **Records cross MCP badly, and it is OPEN — see [`app/docs/mcp-record-crossing-plan.md`](docs/mcp-record-crossing-plan.md).** A record PARAMETER publishes `{type:object}` with no `properties`, so a caller cannot discover the field names, and `FAIL_ON_UNKNOWN_PROPERTIES` being disabled means wrong keys bind all-null and the procedure runs — a silent wrong answer. Separately, `RECORD_MAPPER`'s `withFieldVisibility(ANY)` sweeps the package-private `theLog` into every serialized record, measured at 3.8x payload bloat and enough to overrun a real tool-result limit. **That visibility setting must stay** — it is what dodges the narrowing-accessor `NumberFormatException` fixed in `0d3bc1d` — so suppress those fields by name rather than narrowing visibility. The validation prototype and design/findings record live in `prototypes/mcp/` (`README.md`, `McpDvServer.java`, `smoke_test_generated.py`); the gated live harness is `TGen23aiMcp` (see below).

**Transport exposure — loopback bind + mandatory `Origin` validation (both always on, both runtime-configured).** These implement the MCP spec's two transport security rules and are deliberately **not** propfile flags: one is a MUST, and the other must not be something a config can forget. Both read the environment at run time via **`com.mcpdbwizard.pub.McpHttpPolicy`** (the same pattern as `MCP_HTTP_TOKEN`/`MCP_TLS_*` — nothing baked into generated source, no `Schema` scalar, no GUI/JSON plumbing). (1) **Bind host.** The emitted `http` branch binds **`127.0.0.1`** (`new Server(new InetSocketAddress(theBindHost, thePort))`, and `theSslConnector.setHost(theBindHost)` on the TLS path) — Jetty's own default is every interface, which would put a server whose token and TLS are both opt-in onto the network before anyone chose to. **`MCP_HTTP_HOST=0.0.0.0`** exposes it; note this is also what **publishing 8090 out of the container needs**, and the Dockerfile deliberately does not set it. **Exposure is now coupled to authentication:** binding a non-loopback address **refuses to start (`exit 2`)** unless the server was generated with `MCP_HTTP_TOKEN=YES`, because that one act is what puts the server on a network while both protections are opt-in and fail-closed. **TLS deliberately does NOT satisfy the guard** — it encrypts the wire and restricts nobody, so TLS-without-token is an open server that is merely hard to eavesdrop on. `MCP_ALLOW_UNAUTHENTICATED_EXPOSURE=YES` is the deliberate escape (for a proxy that authenticates upstream) and logs a warning, since disabling a guard should be visible; only `YES`/`TRUE`/`1` count as consent, so a stray empty or `no` value still refuses. This is also why `SchemaDefaults` keeps `mcpHttpToken=NO`/`mcpHttps=NO` — defaulting a fail-closed feature ON would make every new config refuse to start until a secret was supplied. (2) **`Origin` validation.** An always-emitted `jakarta.servlet.Filter` on `/mcp/*`, registered **before** the bearer filter, answering **403** when the header is present and not allowed. The spec requires this (servers *MUST* validate `Origin`) because DNS rebinding makes the attacker's page look **same-origin** to the browser, so the same-origin policy never engages and no preflight is sent — the server-side check is the only thing left. An **absent** `Origin` is allowed (no non-browser MCP client sends one); the literal `null` a sandboxed/`file:` context sends is refused, as is anything malformed. Default allowlist is **loopback only**; **`MCP_ALLOWED_ORIGINS`** (comma-separated) **replaces** that default rather than extending it, so it always states the whole list — include the loopback form if a local browser client still needs it; the single value `*` disables the check. Comparison is normalised `scheme://host:port` with default ports filled in, so `http://localhost` == `http://localhost:80`. **Gotcha the tests exist to prevent:** the loopback test must be a real IPv4 parse, not `startsWith("127.")` — that also admits `127.0.0.1.evil.example.com`, a hostname anyone can register. Unit-tested db-free in `McpHttpPolicyTest` (17 tests, mostly refusals); verified live on FREE23 that the server listens on `127.0.0.1` only, that `MCP_HTTP_HOST=0.0.0.0` moves it to all interfaces, and that an evil/`null` origin gets 403 while an allowlisted one reaches the servlet. **This changes emitted output for any `MCP_SERVER=YES` config** (the `http` branch only) — byte-identity with pre-fix trees is intentionally broken.

Beyond those two, a 2026-08-03 review of the generated server against the MCP spec's transport and authorization rules is written up in [`docs/mcp-security-review.md`](docs/mcp-security-review.md) — what was found sound, the two fixes above, one finding **deliberately accepted**, and **four open items that each need a product decision rather than an edit**. Accepted (2026-08-03, do not "fix"): **every caller is the same Oracle user** — the ordinary three-tier service-account arrangement, and the reason pooled factories are interchangeable at all; the consequences are that the account's grants become the real security boundary (pair least privilege with generation-time curation), that per-user attribution can only come from the MCP layer, and that `USER`-keyed RLS will not discriminate. **The DB password can now come from the environment** (2026-08-03): write **`FROM_ENV_VARIABLE_DB_PASS`** wherever the password would go — as `PASS`, or inside the `DAO_CONNECTION_NAME` URL — and the secret is read from **`DB_PASS`** instead (`com.mcpdbwizard.app.common.DbPasswordSource`). **The sentinel must SURVIVE into the generated code, not be resolved once at load:** the same value is used twice (the generator's dictionary connection, and the emitted factory's runtime connection), so `ConnectionWrangler` calls `resolve` only at the point it opens its own connection and `mrPassword`/`mrURL` keep the configured form, while the emitter calls `toJavaExpression` to produce `"…" + passwordFromEnvironment() + "…"`. Resolving earlier would put the real password back into the emitted source and silently defeat the mechanism. **Note the leak was NOT the `thePassword` field** — that sits behind `oracleVersion.startsWith("DB2")`; on Oracle the factory connects with `getConnection(theUrl)` and no credential properties, so the password rides *inside the URL* (`SAAdminWrangler.java`, the emitted `DriverManager.getConnection (theUrl)` in the Oracle branch — around line 13161, and grep for that statement rather than trusting the number, which has already drifted once), and fixing only `PASS` would have left it intact. Both ends fail closed (generation aborts; the generated factory throws `IllegalStateException` from a field initialiser). **The secret itself comes from either `DB_PASS` or `DB_PASS_FILE`** via `com.mcpdbwizard.pub.EnvironmentSecret`, shared by the generator and the emitted code — the `_FILE` form is the postgres/mysql-image convention and the shape of a Docker/K8s secret mount, and it is the better one (absent from `docker inspect`, **not inherited by child processes** — which matters because the web app forks the generator and the MCP server — tmpfs-backed, rotatable). **The web UI writes the sentinel, never a password** (2026-08-03): its Design connect form asks for host/port/SID/username only, `DesignSession` reads the secret from the environment, and `SchemaDefaults.applyConnection` records `FROM_ENV_VARIABLE_DB_PASS` in **both** `PASS` and the `daoConnectionName` URL — so a web-saved config holds no Oracle secret, and `OracleCredentials` has no password component for one to hide in. **Both set at once is an error, not a precedence rule.** A trailing newline is stripped (`echo secret > file` is how people will make it); a trailing **space is not**, because it may be the password and silently trimming it would read as a wrong credential rather than a mangled one. Opt-in and inert otherwise — a literal password emits the same quoted literal as before, with no helper method. Verified on FREE23: generated code connects for real with `DB_PASS` set, throws when unset, and returns `ORA-01017` when wrong (which is what proves the variable is actually used); zero occurrences of the password or the sentinel anywhere in the tree. **What that review lists as open has moved a long way since — check it, don't quote this paragraph's history.** Three items it originally left open have shipped: OAuth resource-server mode (`MCP_OAUTH`, `5318246` — a static shared token is not MCP's OAuth-based Authorization, and this was never blocked by the accepted item, since it governs who reaches the *server*, not who Oracle sees), the audit trail (the `call(...)` funnel writes an `MCP-CALL` record, with a pluggable sink and a write-ahead spool — `ce2e889`, `9d544ac`, described two paragraphs below), and rate limiting plus a body cap (`120238f`, `3229c1b`). A fourth closed 2026-08-04: **the caller is now named**, by an `MCP-ACCESS` record the web app's `/mcp/{config}` proxy writes — the generated server still cannot name one, so the two records are complementary and correlate by config, tool and time (review §3.4). A fifth closed the same day: **per-caller quotas** (§3.5b), the last item that had been blocked on the generated server being unable to tell two callers apart — `McpCallQuota` keeps a token bucket per account in the proxy, `MCPDBWIZARD_MCP_PER_CALLER_RATE_LIMIT`/`_BURST`, 429 with `Retry-After`. **The two limits layer rather than replace**: a server's own `MCP_RATE_LIMIT` still caps total load and guards it against anything reaching it directly. What is genuinely still open: `SchemaDefaults` sets `mcpHttpToken`/`mcpHttps` to `NO`, which stays deliberate for a fail-closed feature (§3.5a).

**One `MCP-CALL` record per tool call, and the server's output now reaches stdout.** The emitted `call(...)` funnel — the single point every tool handler passes through — writes one line via `com.mcpdbwizard.pub.McpCallRecord`: `MCP-CALL {"tool":"…","outcome":"ok","ms":9,"args":["p_name"]}`. Written in a **`finally`**, so failures are recorded too; outcomes distinguish `ok` / `not-found` / `document-changed` / `pool-exhausted` / `database-error` / `error` (pool saturation was previously invisible and would otherwise read as a database error). The tool name costs nothing to obtain — `req` is the `CallToolRequest` already in scope at all 13 registration sites, so the single `mcpCallOpen` string became `call(req, …)`. **Argument NAMES only, never values:** the values were chosen by a model, which makes them both the most interesting thing to record and the most dangerous, so recording them must be a separate explicit opt-in (not built). It logs through a `JulLog` (`AUDIT_LOG`) rather than the config's own `DAO_LOG_TYPE`, because a console-log config would put these on stdout — the protocol stream on stdio. Separately, `RuntimeManager` no longer redirects the child server's output straight to a file: it **tees**, keeping the file byte-for-byte (the Runtime page tails it, `PoolStats` parses it) and copying to the web app's stdout tagged `[mcp:<config>]`/`[gen:<config>]`, so `docker logs` and any log driver can finally see the generated server at all. **Gotcha:** anything that decides success by *reading* that file — the generation step, looking for its completion marker — must join the tee first, since `Process.waitFor` returns before the pump has drained. This is a diagnostic record, **not an audit trail** (no durability, ordering or tamper-evidence — the audited process writes it); the durable path is the `McpAuditSink` SPI, and since 2026-08-04 the web app's caller-side `MCP-ACCESS` record goes to **the same sink** rather than to a bare logger — the record naming a person used to be the one with no guarantees while the record naming a tool was spooled and replayable, which was backwards. One event type carries both: `McpAuditEvent` gained optional `user`/`config`/`op`/`status` fields that a generated server never sets, so its own records serialise byte-identically. The web app passes a spool *subdirectory* (`McpAuditSinks.fromEnvironment(String)`), because a spool tolerates exactly one writer and the app shares a host with every server it launched. Sink options are weighed in [`docs/mcp-security-review.md`](docs/mcp-security-review.md) §3.4. **Since 2026-08-19 there is also a LOCAL TRAIL that is on by default and is not selected through `MCP_AUDIT_SINK`** — `com.mcpdbwizard.pub.FileAuditSink`, configured by `MCP_AUDIT_FILE_DIR` and `MCP_AUDIT_RETENTION_DAYS` (default 1 day, `0` keeps nothing, and `0` is never inferred: an unparseable value stops start-up). `MCP_AUDIT_SINK` keeps its original meaning — where records go when they leave this machine — and `McpAuditSinks.fromEnvironment` composes the two through **`FanOutAuditSink`** when both are configured, so naming `FileAuditSink` as the sink is refused rather than spooled into two copies of itself. **The emitted code did not change for any of this**: it already calls `fromEnvironment()`, so generated trees stay byte-identical and each server gets its own trail directory because `RuntimeManager` passes `MCP_AUDIT_FILE_DIR=<config-dir>/audit/<config>` per child. `isConfigured()` was widened to mean "anything is recording", since it gates the emitted shutdown hook. Three more streaming sinks ship beside Kafka — **`SyslogAuditSink`** (RFC 5424, octet-framed, no dependency), **`SplunkAuditSink`** (HEC, no dependency) and **`S3AuditSink`** (optional `software.amazon.awssdk:s3`) — and the traps they cost are recorded in [`docs/mcp-audit-sink-plan.md`](docs/mcp-audit-sink-plan.md) §8, of which the one most likely to bite again is that **a TCP write to a closed peer succeeds**, so retry-on-exception silently loses a record per collector restart.

**Observability — an optional Prometheus endpoint (emitted), plus the OpenTelemetry Java agent (attached).** MCP's own in-protocol `logging` utility is **deprecated as of protocol revision `2026-07-28`** ([SEP-2577](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2577)) — the spec's named replacements are stderr on stdio and OpenTelemetry for structured observability — so not adopting it would be the correct posture — **except that abstaining is not on offer, which is why this is now IMPLEMENTED (2026-08-11)**. **The generator does not ask for it and the SDK advertises it anyway.** The emitted `main` builds `capabilities(ServerCapabilities.builder().tools(true).build())`, yet an `initialize` against a running server answers `"capabilities":{"logging":{},"tools":{"listChanged":true}}` (observed on FREE23, SDK 2.0.0). Since the server never sends `notifications/message`, that advertises a deprecated capability it does not implement — an empty promise a client could act on. **Whether the SDK lets it be suppressed is now RESOLVED: it does not.** Both `McpAsyncServer` constructors (the stdio one and the streamable-HTTP one) run `features.serverCapabilities().mutate().logging().build()` unconditionally, so whatever is passed to `.capabilities(...)` is mutated on the way in — "declare only what we implement" is not available at the wire level with this SDK. Note also that the gap was narrower than it read: the SDK *does* implement `logging/setLevel` and filters by a per-session level defaulting to `INFO`, so what was missing was only that our emitted funnel never called `loggingNotification` — an always-empty stream rather than a broken method. **Closed 2026-08-11.** Since the capability cannot be withdrawn, declining to implement would not have put us in the "did not adopt it" camp but in the "claims it and does not do it" camp, which is worse than either honest position; implementing is the cheapest way to make the wire true. The emitted funnel now sends one `notifications/message` per tool call — tool, outcome, elapsed ms, and argument **names only, never values** (the `MCP-CALL` rule, and it matters more here because this frame goes back over the wire). Three properties are load-bearing. (1) **Sent at `DEBUG`**, while a session's threshold defaults to `INFO` and the SDK drops anything below it — so a client that never calls `logging/setLevel` receives **nothing**, and the default costs no traffic and no tokens. (2) **Unconditional, NOT a propfile flag**, for the reason `McpHttpPolicy` is not one: the capability is advertised for every config, so a flag would leave the mismatch in place for every config that forgot it. (3) **The SDK types appear at exactly ONE emitted call site**; the text is built by `com.mcpdbwizard.pub.McpProtocolLog`, which names nothing from the SDK, because `pub` ships with every generated DAO layer and must not drag an MCP dependency behind it — that split is also the deprecation hedge, since removal costs one emitted site and no customer's `pub` jar names the vanished classes. `.capabilities(...)` now also spells `.logging()` at both emission sites: no wire change (the SDK was adding it regardless), but the emitted source stops claiming something different from what it serves, which is what made this hard to find. `TGen23aiMcp` covers it live, and **the negative assertion is the one that matters** — after re-setting the level to `info`, a call must produce NO frame; asserting only the positive would pass equally well if the server ignored the level and sent on every call. Design record, including the four options rejected: [`docs/mcp-protocol-logging-plan.md`](docs/mcp-protocol-logging-plan.md). **Still not fixable from here:** the spec moved level selection onto a per-request `_meta` key (`io.modelcontextprotocol/logLevel`) before deprecating the utility, and SDK 2.0.0 implements only the old request form — the string `logLevel` does not appear in the jar. Attaching the OTel Java agent at run time gives Jetty spans, JDBC spans carrying the SQL, and JVM metrics with no code change and no config surface of our own (OTel's standard `OTEL_*` env vars do everything). **It cannot name the tool that ran:** MCP multiplexes every tool over one endpoint, so all calls arrive as `POST /mcp` and the HTTP spans are indistinguishable — tool identity is only partially recoverable from the JDBC span's SQL. Per-tool `execute_tool` spans would need instrumentation inside the emitted `call(...)` funnel and are **not implemented**; OTel's GenAI/MCP semantic conventions are still *Development* stability at semconv 1.40.0, so deferring is deliberate. **The Prometheus endpoint is what closes that particular gap** (added 2026-08-06, `PROMETHEUS_SERVER=YES`), and the two are complementary rather than alternatives: the agent gives traces the generator could not, and the metrics give per-tool and per-database-object numbers the agent cannot — see the paragraph below. The agent is **safe on stdio** — verified 2026-08-02 with agent 2.14.0 on Temurin 21 that stdout stays at 0 bytes both at startup and while a `OTEL_TRACES_EXPORTER=logging` span is emitted (everything goes to stderr), so it cannot repeat the `DAO_LOG_TYPE=Console Log` protocol corruption. Note the web Runtime path has **no `-javaagent` hook** (`RuntimeManager` builds a fixed child command line), so it needs `JAVA_TOOL_OPTIONS`, which also instruments the web app and the forked generator. Full setup for all three deployment shapes, and why the `POOL-STATS` log line must stay: [`docs/mcp-observability.md`](docs/mcp-observability.md).

**Prometheus metrics (`PROMETHEUS_SERVER=YES`) — measured in the `call(...)` funnel, exposed on a second port.** Optional, default NO, and gated on `MCP_SERVER=YES` (`PROMETHEUS_SERVER` alone logs a warning and emits nothing — there is no "tool call" to measure without a server). It is a **propfile + web-GUI** flag with deliberately **no Swing control**, exactly like `MCP_HTTP_TOKEN` and `MCP_HTTPS`; `Schema.prometheusServer` carries it so `.pb2` ↔ `.json` round-trips, `SchemaDefaults` sets `NO`, and `ApplicationShell` reads it and preserves it on save. Collection lives in **`com.mcpdbwizard.pub.McpMetrics`** and exposition in **`McpMetricsExporter`** (the JDK's own `com.sun.net.httpserver` — no dependency, and it works under stdio as well as HTTP, where there is no Jetty to hang a servlet on). The emitted server gains four things: a `METRICS` field, `METRICS.bindPool(thePool)` on the pooled path, one `METRICS.record(...)` in the funnel's existing `finally` beside the `MCP-CALL` line and the audit sink, and a generated `describeTools()`.

**`describeTools()` is the load-bearing part and the reason this cannot be a pure runtime feature.** At run time the server holds only the tool NAME — a lower-cased, punctuation-stripped Oracle name with an overload number sometimes appended — and one Oracle object routinely yields several tools (a table yields at least four). Nothing can map `ob_gen_pkg_greet` back to `APPSCHEMA.FIXTURE_PKG.GREET` except the generator, so the generator writes it down: **every one of the 13 `.name("…")` emission sites now goes through `SAAdminWrangler.mcpToolNameLine`**, which prints the line *and* records `{toolName, dbObject, objectType}` onto `mcpMetricDescriptions`. That single funnel is the point — a new tool surface cannot be added and silently arrive as an unlabelled series. `TableMcpInfo` gained `tableOwner` for the same reason (`addTableMcpTools` is handed the info object and nothing else, while the owner is resolved back in `buildTableMcpInfo`). A foreign-key child lookup is labelled with the **parent** table, the one it is defined on and keyed by; the child's rows are reachable through the child's own tools, which it must be separately exposed to have.

Metric families, labelled `server` / `tool` / `db_object` / `object_type`: `mcpdbwizard_mcp_calls_total` (counter, additionally by `outcome`), `mcpdbwizard_mcp_call_duration_seconds` (summary — `quantile` 0.5/0.75/0.9 plus `_sum`/`_count`), `mcpdbwizard_mcp_call_duration_seconds_max` (gauge), `mcpdbwizard_mcp_request_bytes_total`/`_response_bytes_total`, and `mcpdbwizard_mcp_pool_*` when pooled. **Three decisions worth not re-litigating.** (1) `outcome` labels the counter but **not** the duration summary — splitting quantiles across seven outcomes computes each from a handful of samples. (2) Quantiles are exact over a **window** of the last `McpMetrics.WINDOW` (2048) calls to that tool, while the **maximum is all-time** — a windowed max discards the worst call the server ever served, which is the one being looked for. (3) `db_object` rides on every series rather than a separate info-metric, so `sum by (db_object)` needs no PromQL join; it is functionally dependent on `tool`, so it costs no cardinality.

**Runtime: `MCP_METRICS_PORT` (unset = no listener) and `MCP_METRICS_HOST` (default `127.0.0.1`).** There is **no default port on purpose** — the web app runs up to twenty servers at once and `TMcpServerStartup` forks twenty-one per box, so a default would give one a socket and the rest a bind failure every run. `RuntimeManager` allocates one per launched server from **`mcpdbwizard.runtime.metrics-port-range`** (empty by default, so nothing changes unless an operator asks) and passes it in the child env. **Failure policy differs from the security guards, deliberately:** an unbindable port is logged and the server keeps serving tools, because refusing to serve because nothing could be told about it is the wrong trade — but an *unparseable* port throws and stops start-up, since that is a typo and the failure being prevented is an operator who believes they are collecting metrics and is not. Likewise a non-loopback bind **warns rather than refusing** the way `McpHttpPolicy` refuses an unauthenticated MCP port: `/metrics` is read-only and carries no database data, though it does publish the schema's object names. **Cost:** inbound volume needs the arguments serialised purely to size them, which nothing else at that level does — so that serialisation is emitted only under this flag, and it sits in front of a database round trip. Tests: `McpMetricsTest` (23, db-free — exact quantiles at small n, the locale-comma trap in the seconds formatting, label escaping of a quoted Oracle identifier, the window/max distinction, concurrent recording) and `McpMetricsExporterTest` (9); the live leg rides `TGen23aiMcp`'s existing HTTP-transport child process, which now also gets `MCP_METRICS_PORT` and is scraped afterwards. All 21 `MCP_SERVER=YES` propfiles set `PROMETHEUS_SERVER=YES`, so the emitter is compiled against every schema rather than one fixture.

### Load and performance testing at the RPC level (`com.mcpdbwizard.loadtest`)

**`com.mcpdbwizard.loadtest.McpLoad` drives a generated MCP server's tools over JSON-RPC directly,
with no LLM in the way**, so throughput and latency can be measured repeatably. An agent-driven
session is slow, expensive and different every time; this is the same protocol at a controlled rate
for a bounded time. It is a **measuring tool, not a test** — nothing in the suite runs it, and it
never starts or stops a server.

It ships inside `mcpdbwizard-app.jar`, which the image already carries at `/app/lib`, so it needs no
build step of its own and cannot drift from the MCP SDK the server is running on:

```sh
java -cp '/app/lib/*' com.mcpdbwizard.loadtest.McpLoad --url http://127.0.0.1:8090/mcp --list
java -cp '/app/lib/*' com.mcpdbwizard.loadtest.McpLoad --url http://127.0.0.1:8090/mcp \
    --workload work.json --for 5m --threads 8 --rate 200 --warmup 30s --out results.json
```

`Scripts/loadtest/mcp-load.sh` is the container wrapper: it finds or starts a server, ships a
workload file in, and reads the server's own Prometheus `/metrics` before and after — a second,
independent count, which is worth more than either measurement alone.

- **`--list` first.** It prints every published tool with its input schema **and a ready-made
  workload entry**, so authoring a workload is copy-and-paste rather than reading generated source
  to find out what a parameter is called. The listing is **paged** — a real schema publishes
  hundreds of tools, and reading only the first page silently under-reports.
- **Both targets, one flag.** `--url .../mcp` is a generated server; `--url .../mcp/{config}` with
  `--token` is the web proxy, which is the path real clients use and the only one carrying the
  per-caller rate limit, the call quota and the token check.
- **`--rate` is OPEN LOOP, and that is the point.** Slots are due at `start + n/rate` and the
  schedule never bends, so a server that slows down does not slow the tool down with it — the run
  falls behind and says how far. A closed loop (sleep a fixed gap *after* each reply) lets the
  server set the rate: ask such a tool for 200/sec against a server that manages 50 and it reports
  50/sec with excellent latency and nothing saying the target was missed fourfold.
- **Two latencies are reported, and only one of them is honest under load.** *Service time* is
  send-to-receive; *scheduled latency* runs from the instant the call was **due**. Measured against
  a deliberately slow server: service time p50 **46 ms** while scheduled latency p50 was **3.78 s**
  and the run achieved 28.6% of its target. Quoting the first alone is the coordinated-omission
  error and makes a saturated server look fast.
- **Templated arguments — `${seq}`, `${thread}`, `${random:a-b}`.** Deliberately three, and
  deliberately not a scripting language. They exist because a hundred thousand calls binding *one*
  value measures Oracle's cursor cache, not the server: a real, repeatable figure describing a
  workload nobody has. A value that is exactly one numeric token keeps its type, so `"${seq}"` binds
  the number 42 rather than the string.
- **`"check": "unique"` is what tells a fast server from a broken one.** Every answer must differ
  and the values must span exactly as many numbers as there were calls — which is what proves each
  call reached Oracle rather than a cache, a retry or a shared result. It is **opt-in per entry**
  rather than keyed off a `_nextval` name suffix, because a check that silently does not run is
  worse than none.
- **Timing accuracy is a measured property, not an assumption.** `LockSupport.parkNanos` overshoots
  in proportion to the wait (0.25 ms after a 1 ms park, 3.3 ms after 20 ms on one ordinary machine),
  which put a **4.4 ms floor** under every scheduled latency in a 50/sec run — the tool measuring
  itself. `RatePacer` therefore parks in halving steps and spins the last 2 ms; after the fix,
  scheduled and service p50 agreed to 0.01 ms.
- **Every named tool is checked against `tools/list` before the run starts.** A typo otherwise
  produces a completed run with a 100% error rate, which reads as a sick server rather than a bad
  command line.
- **Prefer a duration to a call count for anything long**, and use `--warmup`. Throughput climbs
  steeply for the first minute while the JVM JITs, the DAO pool grows and Oracle caches cursors: a
  count sized from a five-second sample of 958/sec once finished in two minutes at 2,403/sec. A run
  reported without a warm-up window is averaging two different systems.

Db-free coverage: `LoadOptionsTest`, `WorkloadTest`, `LatencyDigestTest`, `RatePacerTest`,
`ToolCatalogueRenderTest`, `LoadReportTest`.

Note `IOUtilsTest.grepQuirk_matchAtColumnZeroIsNotFound` is a characterization test: `IOUtils.grep` uses `indexOf(s) > 0`, so a match at column 0 is intentionally not reported — don't "fix" this without updating the test.

Separately, some classes carry hand-rolled self-tests via the `com.mcpdbwizard.test.TestInterface` interface (`getTestName()`, `test(boolean isInteractive)`), invoked from their own `main()` methods. Most of those self-test harness implementations were uncompilable legacy and have been **deleted** (2026-08-01). They were kept under `legacy/test-harnesses/` — described here as gitignored, which was never true: all 25 files were tracked, and 20 of them carried live hostnames and credentials. Nothing referenced them, they did not compile, and the JUnit suite under `src/test/` supersedes them; git history holds them if they are ever wanted. The same commit removed the dead pre-Maven IDE descriptors (`.jpr`, `.jws`, Eclipse `.project`/`.classpath`) that shared that directory.

### Live-DB harnesses (the `generated-tests` profile)

A second tier of tests links against **generator output** and needs a live Oracle DB. These `T*` harnesses live in `src/test/generated-harnesses/`, extend `AbstractLiveDbHarness` (which still implements `TestInterface` and wraps `test(true)` in one gated `@Test`), and are **only compiled when the `generated-tests` Maven profile is active** — i.e. when `target/regen/Src` exists. With no regen tree the profile stays off and `mvn test` runs only the database-free suite above. Harnesses gate themselves via JUnit `Assumptions`, so a missing/unreachable DB skips rather than fails.

The generated code they import is **not checked in** — it is produced by `Scripts/testrun_current.sh`, which for each `Propfiles/generic_test*.pb2` runs the generator (batch mode) against the test DB into `target/regen/Src`, compiles it, and normalises every package label to `ov1210_ov`. (Setting **`OB_JSON_PARITY=1`** turns on a per-propfile JSON-config parity leg: after the `.pb2` generation the runner converts the rewritten `.pb2` to `.json` via `ConfigConverter`, regenerates from the `.json` into the same dir, and asserts the code is byte-identical — comment blocks stripped — restoring the `.pb2` tree before compiling; off by default since it adds one extra generation per propfile. Verified across the canonical set on FREE26. Separately, **`OB_GEN_FROM_JSON=1`** drives the *whole* regen off the `.json` format instead of `.pb2` — each rewritten `.pb2` is converted with `ConfigConverter` and generation runs from the `.json`, so the resulting tree (and everything the `T*` harnesses do with it) is JSON-sourced; used to prove the runtime works off JSON — e.g. `TGen23aiMcp` (the generated MCP server) is green against a full canonical set generated from JSON on FREE26. See also the standalone `Scripts/json-config-test/run.sh` and "JSON config format" above.) **A no-arg run (all 18 propfiles) is green on a 23ai-line box** (verified 2026-07-16: all generate + compile, and `mvn test -Pharnesses-23ai` over the full tree is 280/0/2): the EJB-flavoured `generic_test5/6` (`DAO_EJB=SESSION` + `DAO_LOG_TYPE=Apache's Log4J`) compile against new compile-only shims (`Scripts/compile-shims/javax/ejb/*` + `com/mcpdbwizard/pub/Log4JLog.java`, standing in for the historical EJB container jar and `OBLog4JLog.jar` — the shim dir is already a test-source root of the `generated-tests` profile, so maven gets them too), and `generic_test8`'s AXISTEST `ART` record needed the `plsqlAttrDataTypeDecode` normalizer extended (see below). **A no-arg run is also safe on pre-23ai hosts** (verified against ORCL12: all 17 generate + compile, `mvn test` = 277/0/2 — 18 propfiles today, `generic_test_23ai` having been added since): the hollow `generic_test_23ai` such a run produces (its fixture objects can't exist there) no longer defeats the `no-gen23ai` profile, whose file trigger is keyed to a deep marker (`.../table/manager/FixtureDvMgr.java` — the newest class `TGen23ai` imports) rather than the package directory. **Oracle Spatial: the test path and the product path used to differ, and the product path had nothing (fixed 2026-08-06).** `Scripts/compile-shims` holds compile-only stubs for `javax.jws`, `oracle.xdb` and `oracle.spatial.geometry` so the generated test tree builds on a bare JDK. The first two stopped being stubs in the product long ago — the pom supplies genuine `jakarta.jws-api` and `xdb`. **Spatial now follows them: `com.oracle.database.spatial:sdoapi:23.26` is an `<optional>` dependency**, so the Dockerfile's existing `copy-dependencies` step puts it in `/app/lib` and a spatial config works with no operator action. Before that, such a config compiled under `testrun_current.sh` and *failed* in the web Runtime with dozens of `package oracle.spatial.geometry does not exist` errors naming the symptom rather than the cause — a difference between two compile paths that **no amount of regen testing could see**, because the suite is on the shimmed side. `RuntimeManager.missingSpatialSupport` remains as a safety net, detecting the reference before javac runs.

**Two traps this cost, both worth remembering.** (1) **Oracle DOES publish `sdoapi` to Maven Central** — `com.oracle.database.spatial`, and **only version `23.26` exists**, matching the ojdbc11 23.26.2.0.0 generation. Probing guessed coordinates (`19.3.0.0`, `23.5.0.24.07`) returns nothing and looks exactly like proof of absence; it is not. List [the directory](https://repo1.maven.org/maven2/com/oracle/database/spatial/) rather than guessing versions. (2) **The stub declares API the real jar also has, but the reverse was assumed too quickly.** `JGeometry.store` is overloaded in *both* argument orders — `store(JGeometry, Connection)` **and** `store(Connection, JGeometry)` — and the generator emits both; a `head`-truncated `javap` shows only the first and makes the emitted code look wrong. It is not: the whole generated tree compiles against the real jar with zero spatial errors. **Copying the stub onto the Runtime classpath is still the wrong fix** — every method returns `null`, converting a compile error into a silent wrong answer, and a fake `oracle.spatial.geometry` there could shadow the real jar, silently, with the stub winning. Note `SDO_GEOMETRY` is not JSON-crossable, so these objects yield no MCP tools either way.

**The two run counts above are dated records, and the glob has since grown.** `Propfiles/generic_test*.pb2` now matches **35** files — the 18 originals those verifications covered, plus 17 of the `_mcp` variants described below. The remaining 6 (`connector_*` and their variants) are **outside the glob**, so a no-arg run has never included them; name all 41 explicitly to cover everything. Full workflow:

**The `<name>_mcp` propfile set — the MCP emitter is compiled against EVERY schema, not one fixture (added 2026-08-05).** Until then `MCP_SERVER=YES` was set on exactly **one** of the 21 propfiles: `generic_test_23ai`, whose 28 `OB_GEN_*` routines were written alongside the emitter. The other 20 — `generic_test1` among them, with 313 objects of real APPSCHEMA — generated and compiled only the DAO and SOAP layers; `DaoFactoryMcpServer.java` was never emitted for them, so **no compile had ever seen those tool bodies**. The crossability gate (`mcpProcUnsupportedReason`) and the emitter agreed with each other because both were developed against a fixture chosen to make them agree. There is now a **`<name>_mcp` sibling of every propfile**, differing in exactly three fields so each exercises the emitter under its *own* flags (the `WEB_SERVICES=NO` configs included): `MCP_SERVER=YES`; `TARGET_JVM` (**below 17 the generator emits no server at all, silently** — a variant that forgets this passes while testing nothing); and `PACKAGE_NAME`, so the variant does not generate into the original's tree. Every `_mcp` floor in `Scripts/provisioning/expected-file-counts.txt` is its original's **+1** — the one extra file is the emitted server — which is the quickest check that a number there is right; the two documented exceptions are `generic_test7_mcp` and `connector_none_mcp`, both explained in that file. **The first run found five emitter bugs. ALL FIVE ARE NOW CLOSED** — four in `ae7e7ee` + `0337a75` (2026-08-05), the fifth via `WEB_SERVICES_ABSTRACT_BFILE` below. They were: the package prefix wrongly applied to `com.mcpdbwizard.pub.PlsqlIndexByTable2` (72 errors) and `PlsqlIndexByTable2` not implementing `PlsqlArray`, which `collectionToJson` takes (36) — bugs B and C, **one cause seen from the IN and OUT ends**, since a scalar index-by param yields a **`pub`** class where the collection support assumed a generated one; `protected` record-param field access (12, bug F); and `getParam<X>Nclob()`/`…BooleanObj()` accessor naming (bug D). All four are described where they belong, in the PL/SQL-tool bullet above. Measured across the 41-propfile regen, ORCL21 went 10 propfiles / 196 errors → 0/0 and FREE26 6 / 128 → 0/0. **Consequence for `mvn test`:** the `generated-tests` profile adds *all* of `target/regen/Src` as a test-source root, so while any `_mcp` tree fails to compile a whole-tree `mvn test` stops at test-compile before a single test runs — which is why closing these mattered beyond the trees themselves. **Verified state: all 21 originals and all 20 variants generate and compile on every one of the six boxes, with nothing parked** (`48b0425` onward; the current baseline is `17f3e2b`). **If a tree ever has to be parked again that is a REGRESSION, not routine** — and park all 20 rather than a subset, because which ones fail is Oracle-version-dependent and a tree can pass the regen's own `javac` yet fail Maven's test-compile on a different classpath (`generic_test2_mcp` did exactly that on ORCL12).

**`WEB_SERVICES_ABSTRACT_BFILE` is retired — the key is IGNORED ON READ (2026-08-05).** It made the generated `ServiceImpl` **abstract**, so callers supplied the BFILE upload naming themselves. An `MCP_SERVER=YES` config cannot use such a class: the emitted server instantiates it directly (`new <Factory>ServiceImpl(...)`), and nothing checked the pair, so it surfaced as a `javac` error rather than a refusal. Both GUIs lost the control (the Swing "Uploaded BFILE naming is abstract" checkbox, and the "Abstract BFILEs" select on the web Service Options tab) and now write `NO` on save — but that alone left the setting reachable by hand-editing a config, and the web form binds the **session** schema so a legacy `YES` survived every save. `ApplicationShell` (~line 850) is the only place the flag was ever read, so **ignoring it there** is what makes `YES` unreachable; `webServicesBfilesAreAbstractFlag` now has three assignments in the codebase and all three are `false`, and `SAAdminWrangler`'s five branch sites simply never take the abstract path. `Schema` still round-trips the key so `.pb2` ↔ `.json` stays lossless for old configs; the value just has no effect. **Do not "restore" this as an option without solving the MCP interaction first.**

**Two propfiles declare another propfile's `PACKAGE_NAME`, and a shared package silently merges their trees.** `generic_test7` declared `PACKAGE_NAME=generic_test1...` — so it generated *into* `generic_test1`'s tree, overwrote part of it (including the `DaoFactory`, with a 2-object version), and the harnesses touching `Agents*`/`CollProc7` were linking against test7's output rather than test1's, though the two differ on `WS_PRE/POST_CALL_STUB` and `SQL_CREATE_CLASS`. Fixed 2026-08-05; the suite confirms nothing depended on the overlap. It also made that propfile's file-count floor **fiction** — recorded as 2457, the same number as `generic_test1`, because the counter was measuring test1's tree; test7 really emits 30, so the collapse guard had never checked it and every cross-box "test7 verified" record was re-measuring test1. **The three `connector_*` propfiles had the same collision, fixed the same day.** All three declared `com.mcpdbwizard.mcpdbwizardconnector.test.service` and differ only in `XWS_TYPE` (JSON / JSON-RPC / NONE), so they accumulated in one directory and each reported 618. `connector_none` really emits **600** — the 18 fewer being the connector classes `XWS_TYPE=NONE` correctly does not produce; its 618 was the other two's leftovers counted as its own. Each now has `com.mcpdbwizard.mcpdbwizardconnector.test.<name>`, and all three have real floors for the first time. Nothing depended on the old shared name (the only references were two commented-out lines in `McpDbWizardConnectorGenerator`). **When adding a propfile, give it a `PACKAGE_NAME` of its own** — a shared one does not collide loudly, it merges the trees and makes every file count downstream a fiction.

```bash
mvn -DskipTests package          # build the shaded jar the script drives
Scripts/testrun_current.sh generic_test1 generic_test2 generic_test3 generic_test4 generic_test9 generic_testd
MCPDBWIZARD_TEST_HOST=<host> MCPDBWIZARD_TEST_SID=/<service> \
  MCPDBWIZARD_TEST_URL='jdbc:oracle:thin:@<host>:1521/<service>' \
  MCPDBWIZARD_TEST_USER=<user> MCPDBWIZARD_TEST_PASSWORD=<password> mvn test
```

Key facts (see also the script header and `com.mcpdbwizard.pub.DbTestSupport`):

- **Multi-schema model.** Each propfile introspects its OWN schema named in its `USER`/`PASS` (e.g. `test1/2/3/9` → `APPSCHEMA`, `generic_test4` → `ORINDADEMO`, `generic_testd` → `GENERIC_TESTD`). The script rewrites only host/port/SID + version label and **repoints the baked DAO runtime connection** (`DAO_CONNECTION_TYPE`/`_NAME`) to a direct `jdbc:oracle:thin` URL — it does **not** flatten `USER`/`PASS`. The committed `.pb2` files are never modified (a rewritten copy is generated under `target/regen/work`).
- **`no-gen23ai` profile (file-activated).** Auto-activates when the regen tree lacks a REAL `generic_test_23ai` and excludes `TGen23ai` from the test compile — so base-profile runs against non-23ai boxes need neither the old "stash and restore" ritual nor named propfiles. The trigger is a deep marker file (`.../generic_test_23ai/.../table/manager/FixtureDvMgr.java`, the newest class `TGen23ai` imports) rather than the package directory, so a **hollow** tree — what a no-arg regen produces on a pre-23ai host, or when the OB_GEN fixture was missing — also activates it. Also remember `TGen23ai` DROPS `FIXTURE_TABLE`/`FIXTURE_PKG` in teardown, so re-run `sql/datatypes_23ai_gen.sql` (as appschema) before any FREE23 regen that includes `generic_test_23ai`.
- **`TRecordFieldCensus` — a record generated with NO FIELDS is always a defect, and the census says so.** PL/SQL cannot declare a record without fields (`TYPE r IS RECORD ()` does not compile), so an empty generated record class is *always* evidence that field discovery returned nothing. It needs a test rather than review because it fails in two directions and neither is loud: the Java class comes out bare and **compiles**, and under `EXTRA_SQL` the shadow Oracle TYPE is `CREATE OR REPLACE TYPE x_T AS OBJECT` with no attribute list, which **Oracle ACCEPTS and holds INVALID** — so the `_A` collection on it is invalid too and binds fail at run time, far away. It is also **version-dependent**, which is what let it survive: 12c returns the full `ALL_ARGUMENTS` walk, later versions truncate it and the generator synthesises the fields back, so a record can be perfect on ORCL12 and empty on the other five while all six stay green. Two assertions: no record class without fields, and **every attribute-less type in `extraObjects.sql` carries its `REM WARNING`** — the second has *no allowlist*, being a self-consistency property of the file that holds on every box and version. Both refuse to pass vacuously (an `*Attrs.java`-free tree fails rather than trivially passing). `TOLERATED_EMPTY` is a **ceiling, not a contract**: entries are never asserted to still be empty, because that depends on the version. **It is currently EMPTY, and the seven entries it used to hold are a lesson about allowlists.** They were described as a separate long-standing defect ("empty on ORCL12 too, mostly the Spatial propfile") and **every one was a FALSE POSITIVE of the census itself** — six declare their fields `protected` while the pattern demanded `public`, and the seventh keeps only LOB staging in its `Attrs` class while the `java.io.File` values live in the SUBCLASS that extends it, which the scan never opened. The detector now accepts any access modifier and reads the whole class family. **The census's POSITIVE findings were sound** (`ArrayCommands` and `IbaTestLRec` really did emit zero fields, and the fixes took them to 8 and 6); it was the tolerated list that was noise. The general point: **an allowlist entry is a claim about a failure, and deserves the same checking as the assertion** — an unverified one manufactures a defect that then gets repeated as fact, which is exactly what happened here. **`-Dmcpdbwizard.census.src=<dir>` points it at another tree**, which is how it is proven able to FAIL: a census only ever seen passing is indistinguishable from one that cannot fail, and this repo has shipped two such tests.
- **Logging backends.** Generated factories pick a `LogInterface` from `DAO_LOG_TYPE`. `Java 1.4 Logging` emits **`com.mcpdbwizard.pub.JulLog`** — a `java.util.logging` backend that lives in the main `pub` library, so generated code needs no extra jar. (The older `com.mcpdbwizard.pub.JavaLog`, the same JUL backend kept in the separate `JavaLoggingSrc/` source root — historically the optional `OBJavaLog.jar` — and folded in by the generated-tests profile, is retained but no longer wired to a `DAO_LOG_TYPE`.) Note both `JulLog.getCurrentLog()` and `JavaLog.getCurrentLog()` return the logger name, not a file path. Two further facade backends also live directly in `com.mcpdbwizard.pub`: **`Slf4jLog`** (routes to SLF4J) and **`Log4j2Log`** (routes to Log4j 2, mapping `syserror`→`FATAL`). Both extend `GenericLog`, forward the `Throwable` to the framework on the exception-taking `error`/`syserror` methods, and depend only on the facade/api jar (`slf4j-api` / `log4j-api`), which are **`<optional>` deps in the pom** — apps that use them supply the api plus a binding/impl themselves. They are wired into `DAO_LOG_TYPE` selection: `SAAdminWrangler.LOG_TYPE_DESCRIPTIONS`/`LOG_TYPES` carry **`SLF4J`** → `Slf4jLog` and **`Apache Log4j 2`** → `Log4j2Log` (after the legacy `Apache's Log4J` → `Log4JLog` Log4j-1.x entry, before `User Implemented`), so picking them in the wizard makes the generated `DaoFactory` no-arg constructor emit `new com.mcpdbwizard.pub.Slf4jLog("<logName>")` / `Log4j2Log(...)` with the configured log name — the same `new <class>("<logName>")` shape as the `Java 1.4 Logging` (`JulLog`) / `Log4JLog` branches. (Indices in the two emission ladders are 0 text · 1 console · 2 Java 1.4 (`JulLog`) · 3 Log4J · 4 SLF4J · 5 Log4j 2 · 6 User; existing `.pb2` files are unaffected because `DAO_LOG_TYPE` stores the description *string*, not an index.) You can still instantiate one directly and pass it to a `DaoFactory`. **The deployment can now override that choice at run time** (2026-08-04): the emitted no-arg constructor calls `com.mcpdbwizard.pub.LogBackends.fromEnvironment(<logName>, <factoryClass>)` first and only builds the generated default when that returns null — so **`MCPDBWIZARD_LOG_BACKEND`** (a short name `console`/`jul`/`text`/`slf4j`/`log4j2`, or any `LogInterface` class) replaces it, and an unset variable behaves exactly as before. `DAO_LOG_TYPE` is a *generation-time* answer to a *deployment-time* question — the same config runs in a container, over stdio and standalone, and the right backend differs for each; the audit path already routed around it by hardcoding `JulLog`. **The variable is deliberately NOT named `DAO_LOG_TYPE`**, because this file already records `MCP_HTTP_TOKEN` being both a config flag and an env var as the confusing case that catches people out. A bad value stops start-up rather than silently falling back — an operator who thinks they redirected the logs and did not is the failure being prevented. **Two gotchas the implementation hit:** the `User Implemented` arm's `DAO_LOG_NAME` is a whole constructor expression (`com.acme.MyLog("user.home")`), which is not a name and does not parse inside a string literal — that arm passes the factory class name instead; and any value embedded in an emitted literal now escapes quotes as well as backslashes (`SAAdminWrangler.javaStringLiteral`), where the old `TextLog` line escaped only backslashes. **This changes emitted output for every config**, so byte-identity with earlier trees is intentionally broken; verified by a full canonical regen + `-Pharnesses-23ai` on FREE26 (532/0/2). Rationale and what was deliberately not done: [`docs/logging-plan.md`](docs/logging-plan.md).

## Architecture

Two distinct concerns live side by side: **the generator** (`app`, `mcpdbwizardconnector`) and **the runtime library that generated code links against** (`pub`).

- **`com.mcpdbwizard.pub`** — the runtime support library shipped with generated code. Key types: `QueryStatement` / `DmlStatement` / `CallableStatementParameters` (SQL execution wrappers), `ReadOnlyRowSet` / `WriteableRowSet`, `PlsqlArray` (interface implemented by generated VARRAY/TABLE classes), `PlsqlIndexByTable`, the `CS*Exception` hierarchy, `SessionInfo` (names the Oracle session — see below), and the `LogInterface` logging abstraction (`ConsoleLog`, `TextLog`, `GenericLog`, `UiLog`, plus the framework backends `JulLog` (java.util.logging), `Slf4jLog` and `Log4j2Log`). Changing these signatures affects every program the wizard has ever generated.

- **`com.mcpdbwizard.app`** — the generator application:
  - `app.procbuilder` — the core generation engine (`SAAdminWrangler`, `CallableStatementParameterEngine`, `SqlStatementWrangler`, `ExtraType*`). "Wrangler" classes are the workhorses that turn Oracle metadata into Java source.
  - `app.procbuilder.gui` — Swing UI; `ProcBuilder` is the launcher, `ApplicationShell` the main window, with panels, table models, and the `McpDbWizardEvent` / `McpDbWizardEventListener` mechanism for progress reporting during generation.
  - `app.common` — shared helpers: connection/datatype wrangling, the Oracle DDL object model (`OracleDdlObject`, `OracleFunction`, `OracleSequence`), and name legalization (`LegalOracleNameWranger`).
  - `app.templates` — `TemplateWrangler` performs template-based file generation.

- **`com.mcpdbwizard.util` + `util.files`** — `StoredFile` abstraction. The `*_txt` / `*_bat` classes (e.g. `GenericBatchTxt`, `GenericCompileTxt`) are **template files encoded as Java classes**: they hold arrays of text lines containing `PARAM_*` placeholder tokens that the generator substitutes at output time.

- **`com.mcpdbwizard.schema`** — a JSON-friendly, typed model of a generation request (the same information a `.pb2` holds): `Schema` + `Sequence` / `Table` / `Procedure` / `SqlStatement` / `SqlParam`, with a small dependency-free `Json` reader/writer. Converts both ways (`Schema(Properties)`/`toPb2()` ↔ `Schema(String)`/`toJson()`), letting the app run off `.json` configs as well as `.pb2`. See "JSON config format" under Build & run.

- **`com.mcpdbwizard.mcpdbwizardconnector`** — newer generator that emits JSON / JSON-RPC connector code from a list of PL/SQL methods (`BaseMethodRepresentation`, `JSONMethod`).

- **`com.mcpdbwizard.prod` — DELETED 2026-08-07, do not restore it.** It was a checked-in example of generator output (a DAO factory, table managers and SQL/PL-SQL wrappers for an "osoft hosts/netblock" schema, plus an `IpBrowser2` driver), emitted in **2007** and never regenerated since. It could not be brought up to date: its schema exists on no test box and no propfile targets it, so nothing in the repository could reproduce it. That made it a reference showing 2007 idioms and a dead vendor URL to anyone who copied from it. **`app/sql/Demo/Src` is the replacement** (published as `examples/generated-output/`, the one thing lifted out of `sql/` for the open-source cut, because it is generator OUTPUT rather than DDL) and serves the same purpose better — it was regenerated from a live `ORINDADEMO` schema in the same commit, so it shows what the generator actually emits today. Git history holds the old tree if it is ever wanted.

## Conventions & gotchas

- **`PARAM_*` tokens are intentional, not bugs.** Strings like `PARAM_PRODUCT_NAME`, `PARAM_AUTHOR`, `PARAM_CODE_BASE_DIRECTORY`, `PARAM_JDBCJAR` appear in ~60 files (template files, Javadoc headers, generated-code scaffolding). They are placeholders substituted at generation/build time — do **not** "fix" or fill them in. **The test is whose file the token ends up in.** A token the generator writes into a *customer's* generated output must stay a token; one merely left unsubstituted in *our own* source is just an unfinished header. `PARAM_COPYRIGHT_NOTICE` was the second kind — it never reached generated output — and all 45 of its occurrences were replaced with this project's real notice on 2026-08-04, so it no longer appears anywhere. The rest are the first kind; leave them alone.
  **Sharpened 2026-08-11: "whose file" is not the whole test — the real question is WHICH MECHANISM processes that file.** A token only survives to be substituted if it sits in a file the substituting pass actually reads. `PARAM_JDBCJAR` is genuinely substituted, by `AbstractBaseStoredFile`, which processes the `StoredFile` `.bat` templates and nothing else. `SAAdminWrangler` was printing it into the emitted MCP server's usage comment through `theJavaCode.print(...)`, a path that pass never sees — so a customer got the literal text `<PARAM_JDBCJAR>` on a classpath line, between two neighbours (`<generated classes>`, `<MCP SDK jars>`) that were already plain prose. Fixed by making it prose too. **Before adding a `PARAM_` token anywhere, name the code that will replace it**; if that code does not read the file you are writing, you are shipping the token.
- **Class names are PascalCase.** All type names now follow Java convention (e.g. `ProcBuilder`, `ConnectionWrangler`, `SqlStatementWrangler`); the older lowercase-first / snake_case names (`procBuilder`, `connectionWrangler`, `generic_batch_txt`, …) have been migrated. Note that *package* segments remain lowercase (e.g. `com.mcpdbwizard.app.procbuilder`), and method/field/variable names retain their original (often lowercase-first) spellings.
- The project uses the standard Maven layout under `src/main/java`. The obsolete pre-Maven IDE descriptors (`.classpath`, `.project`, `.jpr`, `.jws`) that used to sit in `legacy/` were deleted 2026-08-01 along with that directory.
- This is the **default branch (`main`)** workflow with no PR process configured; commit/push only when explicitly asked.
